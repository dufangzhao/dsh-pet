## 文档制作规则

1. 用户明确表达的目标记为“已确认”；首版范围、供应商或框架没有被选择就保持“待选”。
2. 每次只询问一个关键决策。先用具体使用场景解释，再讲技术名词。
3. 每个选项说明：带来什么、失去什么、实现/维护代价、何时适合、将来能否换。
4. 难以逆转且存在真实取舍的已选决策，另写简洁 ADR；不为每个小配置制造 ADR。
5. 单元测试、官方宣称、静态源码与真实运行验证分别记录。调研未运行目标应用。
6. 文档与研究材料纳入 Git；不主动创建远程仓库、推送或发布。
7. 当前只做文档和选型；用户确认达到可开工状态后才实施产品代码。

## 后续交付物（按决策成熟度创建，不先堆空模板）

- PRD：用户、场景、首版范围、非目标、关键流程、异常和验收标准。
- 总体架构：进程、模块、数据与权限边界、部署方式、替代路径及理由。
- 插件 SDK / 契约：清单、发现、配置、生命周期、能力协商、事件、流、取消、UI贡献点、兼容迁移。
- 能力规格：语音输入、听写注入、TTS、音色制作、角色、视觉、电脑操作、Agent及记忆。
- 设置与交互规格：信息架构、默认值、生效方式、状态反馈、错误恢复、键盘与无障碍。
- 安全与隐私：授权、密钥、屏幕/录音数据、插件信任、更新、审计与紧急停止。
- 工程与发布：仓库、开发环境、Git工作流、CI、打包、升级、许可与供应链。
- 任务分解：依赖关系、独立写入范围、产物、测试、完成定义和验证型原型。

## 可开工检查门槛

- [ ] 产品形态、首发平台、目标用户与发布/许可路径已选择。
- [ ] MVP和后续版本分开，首版有明确用户闭环。
- [ ] 插件开放边界与UI贡献点明确，不能只写“高度可扩展”。
- [ ] 关键技术路径有理由、备选及待验证风险，未知项有验证任务。
- [ ] 每条首版能力有输入输出、状态、错误、取消、权限和验收标准。
- [ ] 性能目标有测量环境/负载/指标/阈值；没有把模型延迟与UI卡顿混为一谈。
- [ ] 任务粒度能直接交给开发者或编码Agent，且每项有完成定义。
- [ ] 用户确认共识。可先启动有限验证原型，不代表所有风险已消除。
