# 功能插件、提供者与拆卸生命周期 v0.1

状态：用户明确希望较独立功能成为可拆卸模块；现有决策已确认能力/插件中心及受控UI。本文建议采用“两层插件”，具体粒度等待Q9确认；未创建产品插件代码或锁定运行框架。

## 不要混淆三件事

- 功能可配置：在同一大模块里修改选项，不一定可替换实现或卸载功能。
- 提供者可替换：同一能力可换实现，但功能流程可能仍固定在主程序。
- 功能可拆卸：一个功能及其UI入口、任务、热键、资源归属都由可管理模块承载。

用户要求的是第三层能力，并保留前两层的灵活性。

## 建议结构：小宿主 + 功能插件 + 能力提供者

### 基础宿主

保留启动、插件管理、任务/取消、配置、授权/凭据代理、贡献点注册与至少一个稳定设置/退出入口。内部可以模块化，但不允许普通卸载操作破坏基础启动与管理能力。

宿主不固化ASR算法、TTS供应商、角色专属表现或某个业务流程。插件框架可管理依赖与生命周期，但媒体流、权限、故障隔离与兼容治理仍是产品职责。

### 功能插件

承载一个完整用户功能及其设置、命令、结果面板和流程。

| 功能示例 | 依赖的能力 | 当前范围 |
| --- | --- | --- |
| 语音听写 | 音频采集、ASR、文本提交 | 首条正式闭环已确认 |
| 朗读 | 文本来源、TTS、播放 | 总体需求，版本安排待选 |
| 语音聊天 | 音频/ASR、Agent、可选TTS | 总体需求，版本安排待选 |
| 声音制作 | 制作/克隆服务、声音资源管理 | 深度与版本待选 |
| 屏幕问答 | 捕获、OCR/VLM、结果展示 | 范围与版本待选 |
| 电脑操作 | Agent/任务编排、观察、执行器 | 自动化深度与版本待选 |

### 能力提供者插件

实现稳定能力契约，例如本地ASR、云ASR、某家TTS、Windows文字输入、浏览器操作等。同类提供者可选择或替换；一个提供者可被多个功能使用。

音频采集、平台输入等通用能力究竟单独成包还是由平台服务包提供，后续按重用、进程与权限边界确定。两层逻辑不意味着把每个函数、按钮都拆成单独插件。

### 功能套装与首次安装

普通用户可以只看见“安装听写功能”，宿主展示并管理其所需模块。套装是依赖组合，不把实现永久焊在功能里。

首版本地和云端ASR均需实际可用，不等于必须把全部模型权重捆进安装包或默认启用全部插件。具体预装、按需下载与重装来源待发行方案确认。

## 依赖原则

1. 功能依赖能力契约，不直接调用另一插件的私有函数或读取其数据目录。
2. 宿主检查必需/可选能力与兼容范围，并记录当前使用哪个提供者。
3. 更换默认提供者对新任务生效；运行中的识别/播放不静默混用两个版本。
4. 卸载功能不直接删除仍被其他功能使用的共享提供者、运行时、声音或模型。
5. 依赖缺失时给出解释与修复入口，不隐藏功能失败，也不擅自安装/运行新代码。
6. 本地ASR卸载后若只剩云端，不能未经批准自动向云上传；应先让用户确认切换或保持未就绪。

## 安装、启用、停用和卸载不是同一操作

| 操作 | 语义 | 必须考虑 |
| --- | --- | --- |
| 安装 | 准备包与元数据 | 来源、版本、兼容、许可；安装脚本可能执行代码，不能忽略 |
| 配置/授权 | 为具体用途准备参数与访问 | 配置完整不等于获得所有系统权限 |
| 启用 | 注册能力与界面，开始所需运行 | 缺依赖/权限/模型应报告未就绪 |
| 停用 | 保留包但停止提供功能 | 拒绝新任务、取消/收尾、撤销入口与监听、释放资源 |
| 卸载 | 移除可卸载包及注册信息 | 依赖检查、数据去留、正在运行的代码/锁定文件 |
| 更新 | 将包切换到新版本 | 任务收尾、数据迁移、失败回滚与兼容检查 |

需要受控重启才能更新/删除原生组件时，应显示“待重启完成”，不能声称任意插件都能无条件热卸载。进程未停止或清理失败时不能显示已经卸载完毕。

## 停用/卸载顺序（建议）

1. 标记不再接收新任务，并停止暴露可触发的新入口。
2. 取消或按策略结束所属任务，阻止晚到事件复活已停用功能。
3. 清理热键、订阅、定时器、面板、音频/GPU会话与所属进程。
4. 释放对共享能力的引用；不误停仍被其他功能使用的资源。
5. 仅在可确认清理完成后变更状态；失败则显示原因、隔离或提供重启修复。
6. 卸载时让用户知道是否保留配置/记录/模型。删除云端资源、个人音色或共享凭据不能与删除插件包混为一谈。

停用用于撤销实际能力，不只是把开关变灰。对拥有完整OS权限的第三方原生代码，宿主能强制到什么程度需要隔离设计与测试，不能凭这套顺序就宣传为安全沙箱。

## 与丝滑体验的关系

- ASR/TTS推理、模型下载和原生任务不阻塞角色/设置UI。
- 面板通过标准状态事件更新，不直接驱动无限高频的全局渲染。
- 任务与媒体队列有边界，取消/背压能传播；停止后旧音频和旧输入不能继续提交。
- UI贡献点遵守主题、焦点与通知规范；用户能控制哪些入口固定在角色旁。
- 核心管理与停止入口不因某个功能插件异常而消失。

数值性能预算及具体隔离方案仍待选择；这不是已经完成的性能保证。

## 开发者体验建议

- 官方功能也使用同一套公开能力/贡献点契约，以测试证明第三方可做等价扩展。
- 提供最小模板、类型/schema、配置说明和生命周期测试；版本与不兼容原因可见。
- 将“开发时热重载”与“生产中安全更新”分别实现，不混为一项承诺。
- 普通配置与高级诊断分层；无需让用户为了启用功能手工拼接内部服务。

## 两条可选拆分路径

**A 两层插件（推荐）**：功能插件组织流程和UI，提供者插件实现底层能力。初期契约工作更多，但能共享、替换和独立升级ASR/TTS等。

**B 先做较大的功能插件**：听写包内带其识别/输入等实现，功能包之间可拆卸。起步较快、安装关系简单，但跨功能共享与只替换某个引擎更容易产生耦合，后续进一步拆分成本更高。

两者都不意味着必须开发公开插件市场；发行来源、包格式和信任分级另行确定。
