# 统一插件模型与拆卸生命周期 v0.2

状态：用户提出功能插件与提供者应采用类似DSH的统一单层模型。本文据此修订为同一种插件标准、统一管理与能力依赖图；“功能/提供者”仅是职责，不建立两套插件层级。完整表述等待Q9确认；未创建产品插件代码或锁定框架版本。

## 不要混淆三件事

- 功能可配置：在同一大模块里修改选项，不一定可替换实现或卸载功能。
- 提供者可替换：同一能力可换实现，但功能流程可能仍固定在主程序。
- 功能可拆卸：一个功能及其UI入口、任务、热键、资源归属都由可管理模块承载。

用户要求的是功能可拆卸，并保留配置与提供者替换的灵活性；上述是三个概念，不是三个插件层级。

## 建议结构：小宿主 + 平级插件注册表

### 基础宿主

保留启动、插件管理、任务/取消、配置、授权/凭据代理、贡献点注册与至少一个稳定设置/退出入口。内部可以模块化，但不允许普通卸载操作破坏基础启动与管理能力。

宿主不固化ASR算法、TTS供应商、角色专属表现或某个业务流程。插件框架可管理依赖与生命周期，但媒体流、权限、故障隔离与兼容治理仍是产品职责。

### 同一种插件可以承担功能编排职责

这类插件组织一个完整用户功能及其设置、命令、结果面板和流程。它与提供ASR/TTS等能力的插件使用同一登记/配置/生命周期标准，不属于更高层级；同一插件也可以同时提供能力。

| 功能示例 | 依赖的能力 | 当前范围 |
| --- | --- | --- |
| 语音听写 | 音频采集、ASR、文本提交 | 首条正式闭环已确认 |
| 朗读 | 文本来源、TTS、播放 | 总体需求，版本安排待选 |
| 语音聊天 | 音频/ASR、Agent、可选TTS | 总体需求，版本安排待选 |
| 声音制作 | 制作/克隆服务、声音资源管理 | 深度与版本待选 |
| 屏幕问答 | 捕获、OCR/VLM、结果展示 | 范围与版本待选 |
| 电脑操作 | Agent/任务编排、观察、执行器 | 自动化深度与版本待选 |

### 同一种插件也可以承担能力提供职责

这类插件实现能力契约，例如本地ASR、云ASR、某家TTS、Windows文字输入、浏览器操作等；它们也可以提供自己的设置页、命令或诊断面板。同类实现可选择或替换，一个实现可被多个插件使用，不需要特殊的“底层插件类型”。

一个插件既能消费能力，也能提供能力和UI贡献点。实际拆包按复用、独立启停、资源归属和升级需求确定，不为满足“层数”把每个函数或按钮拆包。音频采集/平台输入可单独成包，也可由适当的平台服务包提供；包格式后定。

### 功能套装与首次安装

普通用户可以只看见“安装听写功能”，宿主展示并管理其所需模块。套装是安装/配置组合，不是新的插件层级，也不把实现永久焊在功能里。

首版本地和云端ASR均需实际可用，不等于必须把全部模型权重捆进安装包或默认启用全部插件。具体预装、按需下载与重装来源待发行方案确认。

## 统一标准，而非统一职责或来源

```text
统一 PluginHost / 插件管理器
  ├─ 听写插件          消费：音频、ASR、文本输入；贡献：命令、设置、状态UI
  ├─ 本地ASR插件       提供：ASR；贡献：模型设置/诊断
  ├─ 云ASR插件         提供：ASR；贡献：服务商与凭据设置
  ├─ Windows输入插件   提供：文本输入；贡献：兼容性诊断
  ├─ 朗读插件          消费：TTS、播放；贡献：朗读命令/面板
  ├─ TTS插件           提供：TTS；可消费其他能力
  └─ 其他官方或外部插件 使用同一套插件/能力/贡献点契约

依赖示例：听写 → speech.asr（由宿主路由到已选择的本地或云实现）
          语音聊天 → speech.asr（可复用，不另建一份固定引擎）
```

上图为契约关系示意，插件ID和接口名尚未冻结，不代表产品已实现。

| 维度 | 用途 | 不意味着什么 |
| --- | --- | --- |
| 提供/消费的能力 | 解析依赖与路由 | 不把插件分成不可跨越的上下层 |
| 功能/接入/工具/外观标签 | UI筛选与说明，可多选 | 不是不同SDK或不同加载器 |
| 官方预装/官方按需/第三方 | 来源、分发与维护信息 | 来源不能由插件自称后自动变成高权限 |
| 必需核心/可选功能 | 保护启动与管理入口 | 内置的所有功能都必须不可卸载 |
| 运行位置与信任级别 | 隔离、权限与性能治理 | 平级插件必须在同一个进程运行 |

官方可选功能可以默认随产品提供，但仍遵守同一契约。基础加载/管理/停止等少量核心模块可标为受保护，避免用户把恢复入口卸掉；可选预装与用户后装模块都应有清晰的启停/卸载状态。

同一ASR能力可有多个实现同时注册，宿主按显式选择路由，不允许“后加载覆盖先加载”成为隐式选择规则。预装只是默认组合，不将某一家引擎直接写死在听写流程里。

## 单层逻辑模型与运行隔离是两件事

插件可以通过宿主侧入口、受控UI入口或进程外适配器参与同一契约。重计算、原生代码和不可信内容如何隔离，仍要单独设计；同一套manifest与生命周期不要求相同的执行环境。

Cordis的统一注册/服务依赖/清理机制可作为候选基础，但跨进程代理、媒体流、强权限执行和多提供者路由仍需产品契约。核查资料见[平台调研](../research/tech-platform.json)。不能把逻辑上的统一模型等同于复制DSH的全部执行或权限策略。

## 依赖原则

1. 任一插件都通过声明的能力契约依赖其他插件，不直接调用其私有函数或读取私有数据目录。
2. 宿主检查必需/可选能力与兼容范围，并记录实际提供者；无法解析的必需依赖/环明确报错，不靠加载顺序碰运气。
3. 更换默认提供者对新任务生效；运行中的识别/播放不静默混用两个版本。
4. 卸载功能不直接删除仍被其他功能使用的共享提供者、运行时、声音或模型。
5. 依赖缺失时给出解释与修复入口，不隐藏功能失败，也不擅自安装/运行新代码。
6. 本地ASR卸载后若只剩云端，不能未经批准自动向云上传；应先让用户确认切换或保持未就绪。

## 安装、启用、停用和卸载不是同一操作

| 操作 | 语义 | 必须考虑 |
| --- | --- | --- |
| 安装 | 准备包与元数据 | 来源、版本、兼容、许可；安装脚本可能执行代码，不能忽略 |
| 配置/授权 | 为具体用途准备参数与访问 | 配置完整不等于获得所有系统权限 |
| 启用 | 注册能力与界面，开始所需运行 | 缺依赖/权限/模型应报告未就绪 |
| 停用 | 保留包但停止提供功能 | 拒绝新任务、取消/收尾、撤销入口与监听、释放资源 |
| 卸载 | 移除可卸载包及注册信息 | 依赖检查、数据去留、正在运行的代码/锁定文件 |
| 更新 | 将包切换到新版本 | 任务收尾、数据迁移、失败回滚与兼容检查 |

需要受控重启才能更新/删除原生组件时，应显示“待重启完成”，不能声称任意插件都能无条件热卸载。进程未停止或清理失败时不能显示已经卸载完毕。

## 停用/卸载顺序（建议）

1. 标记不再接收新任务，并停止暴露可触发的新入口。
2. 取消或按策略结束所属任务，阻止晚到事件复活已停用功能。
3. 清理热键、订阅、定时器、面板、音频/GPU会话与所属进程。
4. 释放对共享能力的引用；不误停仍被其他功能使用的资源。
5. 仅在可确认清理完成后变更状态；失败则显示原因、隔离或提供重启修复。
6. 卸载时让用户知道是否保留配置/记录/模型。删除云端资源、个人音色或共享凭据不能与删除插件包混为一谈。

停用用于撤销实际能力，不只是把开关变灰。对拥有完整OS权限的第三方原生代码，宿主能强制到什么程度需要隔离设计与测试，不能凭这套顺序就宣传为安全沙箱。

## 与丝滑体验的关系

- ASR/TTS推理、模型下载和原生任务不阻塞角色/设置UI。
- 面板通过标准状态事件更新，不直接驱动无限高频的全局渲染。
- 任务与媒体队列有边界，取消/背压能传播；停止后旧音频和旧输入不能继续提交。
- UI贡献点遵守主题、焦点与通知规范；用户能控制哪些入口固定在角色旁。
- 核心管理与停止入口不因某个功能插件异常而消失。

数值性能预算及具体隔离方案仍待选择；这不是已经完成的性能保证。

## 开发者体验建议

- 官方功能也使用同一套公开能力/贡献点契约，以测试证明第三方可做等价扩展。
- 提供最小模板、类型/schema、配置说明和生命周期测试；版本与不兼容原因可见。
- 将“开发时热重载”与“生产中安全更新”分别实现，不混为一项承诺。
- 普通配置与高级诊断分层；无需让用户为了启用功能手工拼接内部服务。

## Q9澄清与待确认表述

此前建议把“功能编排/能力提供”称为两层，用户指出DSH中它们属于同一层、功能插件主要只是官方自带。这个反馈没有选择原A或B，不能记成已经接受两层模型。

修订建议：**所有插件同一种标准、同一注册/管理与生命周期模型；插件可提供和消费能力，也可贡献UI；职责标签与来源不形成架构层级。通过能力依赖图保留细粒度共享和替换，不退回把全部实现焊进大功能包。**

用户确认这一表述后再形成正式ADR。框架版本、包格式、运行隔离和公开插件市场仍另行选择。
