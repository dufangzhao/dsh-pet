# 扩展产品规格 v0.1

状态：开放模式已确认（Q1=B）；实现技术、具体首版贡献点和数值验收阈值尚未冻结。决策依据见[ADR-0001](adr/0001-controlled-ui-contributions.md)。

## 使用者应该得到什么

- 普通用户能按需安装/配置/启用插件，不必理解底层框架。
- 安装一个新功能，可以出现必要的设置与使用入口，而不总要等待主程序升级。
- 同一类能力可选择不同实现，插件品牌不改变基本操作和取消方式。
- 开发者知道可以扩展哪里、输入输出是什么、如何测试、何时需要用户授权。

## 功能本身也应可拆卸

用户进一步明确，不仅要在设置里换模型/供应商，也要让听写、朗读等相对独立功能作为可拆卸模块。功能应拥有自己的入口、任务和资源；停用/卸载不是只隐藏一个按钮。用户进一步提出平级的统一插件模型：职责和来源不分架构层。修订建议及共享依赖处理见[统一插件模型与生命周期](11-plugin-composition-and-lifecycle.md)，Q9已确认统一单层模型，见[ADR-0010](adr/0010-unified-plugin-model.md)。

## 候选贡献点

以下描述开放方向；是否全部进入首版，待MVP确认。

| 贡献点 | 插件提供 | 宿主管理 | 使用例子 |
| --- | --- | --- | --- |
| 能力提供者 | 能力声明、配置和实现 | 选择/路由、权限、生命周期、故障状态 | 新ASR/TTS或翻译服务 |
| 设置页/设置分组 | 字段或受控面板与说明 | 导航、搜索入口、主题、保存/生效状态 | 翻译语言和词汇表 |
| 命令/快捷操作 | 动作声明、参数、可用条件 | 用户绑定、焦点/冲突、权限与执行状态 | 选中文本后翻译 |
| 角色旁快捷按钮 | 图标、文案与命令引用 | 用户选择是否固定、排序和数量限制 | 朗读/翻译/截图入口 |
| 结果/任务面板 | 结构化结果或受控自定义内容 | 打开/关闭、状态、取消、布局与主题边界 | 翻译结果、下载进度 |

不把“任意修改主程序DOM”“任何插件都能读所有密钥”“无条件后台操作电脑”当作扩展能力。

## 示例闭环：第三方翻译插件

1. 用户查看功能、版本和所需访问，决定安装。
2. 配置服务，确认哪些数据会外发，再启用。
3. 设置台出现翻译配置；用户可以将翻译命令固定到桌宠快捷区。
4. 点击后先显示已受理/处理中，再逐步显示结果；角色仍可拖动，设置仍可操作。
5. 用户取消时终止相关工作，并丢弃晚到结果。
6. 停用/卸载后入口消失，任务/监听停止；是否删除用户数据另有明确选择。

这些是期望行为，不代表已经实现。

## 流畅性与可靠性要求

- 入口反馈不以远程模型完成为前提；不得伪报任务完成。
- 计算、下载、识别、合成与常规UI交互解耦；单插件慢不能冻结宿主。
- 隐藏或停用面板应释放/暂停不需要的工作，避免不可见页面持续渲染。
- 设置标注立即生效、重载插件或重启应用；保存失败须回滚显示或明确保留未保存状态。
- 错误可定位到具体插件，用户能重试、停用或降级；不把所有失败呈现为“AI出错”。

## 验收场景候选

| 场景 | 预期 |
| --- | --- |
| 更换同类提供者 | 不改用户工作流；缺少能力时明确提示，而非偷偷改变语义 |
| 插件激活失败 | 不影响桌宠/设置台；入口不可误显示为可用 |
| 运行中停用 | 有界取消并清理入口/监听/任务；后台无遗留工作 |
| 两插件请求同一热键 | 明确冲突，交给用户选择，不静默覆盖 |
| 慢TTS/网络中断 | 输入/拖拽可用，状态可取消，失败有可行动信息 |
| 插件API不兼容 | 启用前阻止或明确兼容措施，不到执行中才崩溃 |
| 自定义面板越权请求 | 宿主拒绝并可解释；面板样式不能伪装宿主授权 |

## 待决定的技术问题

- 内核与框架、桌面壳、界面框架，以及是否fork现有项目。
- 内置/可信/第三方插件的信任分层、进程或沙箱方案。
- 贡献点首版范围：schema表单与自定义面板是否同时开放。
- 插件语言、包格式、版本兼容策略、安装源和更新渠道。
- 性能预算、崩溃隔离、资源上限和测试SDK。
