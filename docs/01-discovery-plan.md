## 已回答 Q1：插件可以把产品扩展到什么程度？

状态：2026-10-24，用户明确选择B，已采纳。见[ADR-0001](adr/0001-controlled-ui-contributions.md)和[扩展产品规格](03-extension-product-spec.md)。

### A · 能力可换，普通界面基本固定

插件可以换模型、ASR/TTS、添加Agent工具、资源和高级配置；普通设置/桌宠快捷入口主要由产品维护。

- 直观例子：装入一个新TTS，就能在声音下拉框里选它，但它不能给桌宠加一个全新工作面板。
- 优点：规则少、界面一致、容易控制性能和支持成本；接近Coopanion文档中的普通界面边界。
- 缺点：复杂扩展要借高级面板、聊天或另开应用；新交互常需改主产品。
- 适合：首要目标是快速交付完整桌宠，而不是建设插件平台。

### B · 能力 + 受控界面贡献点（推荐）

插件除提供能力外，可按标准注册设置页、快捷命令/按钮、任务面板等；宿主负责入口、布局、主题、权限和启停。首版只开放少量必要贡献点，保留可扩充的规范。

- 直观例子：翻译插件添加自己的设置页、一个用户可固定到桌宠旁的翻译按钮，以及统一风格的结果面板；卸载后入口和任务一起清理。
- 优点：不改主程序也能增加完整功能；普通用户仍看到一致的界面；更吻合“扩展强+交互顺”。
- 代价：必须认真设计UI契约、配置schema、生命周期、兼容测试和慢插件隔离，不能只做一个加载文件夹。
- 限制：插件不能任意修改主界面DOM、绕过权限或劫持全局快捷键；复杂自定义UI须通过独立受控面板等通道。

### C · 可重组工作台，较广泛开放布局与复杂界面

允许插件提供复杂面板/独立应用界面，用户可重组更多工作区布局与交互。安全内核仍不能被插件改写。

- 直观例子：插件能提供一整套多面板工作台，而不只是几个标准入口。
- 优点：表达能力最强，更适合开发者生态和复杂工作流。
- 代价：产品重心接近扩展平台；跨插件风格、性能、键盘焦点和版本兼容更难，首版范围明显扩大。
- 适合：愿意把平台能力而非实用桌宠闭环作为第一阶段重点。

以上是工程选型说明，不代替具体发布场景的法律审查。代码、SDK、插件、模型权重、声音和角色资产分别授权。

## 已回答 Q4：以什么作为架构中心？

状态：2026-10-24，用户选择A。已采纳[ADR-0004](adr/0004-capability-centered-host.md)；先确定能力/插件中心，不提前冻结具体框架版本。

### A · 能力/插件中心，采用合适的现成插件框架（推荐）

语音、TTS、角色、模型、视觉、电脑操作分别作为能力；Agent也是可替换能力之一，不是每条工作流的必经入口。例如听写可以直接转录并提交到目标，而无需先交给LLM规划。

- 收益：符合实用、可替换和受控UI贡献点的要求；能力依赖清楚。
- 成本：需定义能力契约、路由、UI贡献点、权限代理、媒体流和任务生命周期。
- 框架候选：Cordis提供服务依赖/生命周期等基础，不等于引入完整DSH，不提供自动OS沙箱。具体发行线与API稳定性需锁定版本并做小型验证。
- 技术含义：倾向JS/TS能力宿主；桌面壳和重计算实现仍可另选。

### B · Cortico智能体内核中心，另外实现本项目UI和能力桥接

以MIT Cortico Core的角色/会话/事件/工具组织作为主要基础。可复用智能体编排；并非复制AGPL Coopanion产品界面或桌宠World。

- 收益：较多现成会话与角色编排基础可用，贴近Coopanion底层组织。
- 成本：要适应World/Persona/Provider语义；独立听写、ASR/TTS统一能力插槽、受控UI和强权限边界仍需补建。
- 边界：不是说该框架不能实现直接工作流，而是需要额外桥接，不能假定产品代码与框架一并可用。

### C · 插件基础设施也全部自建

自行实现注册、依赖、启停、配置与调度，而不采用现成插件框架。

- 收益：控制直接，不跟随特定框架API变更。
- 成本：依赖排序、失败清理、重载、兼容和诊断都需要自己维护。小原型可以很短，完整强扩展平台并不一定更简单。

框架选型不是安全验证；无论哪条路，都必须单独确定插件信任、进程隔离、权限和验收。

## 已回答 Q6：先把哪条实用闭环做到日常可用？

状态：2026-10-24，用户选择A。首条闭环为语音听写到目标应用，见[ADR-0007](adr/0007-dictation-first-workflow.md)及[听写PRD](09-dictation-mvp-prd.md)。不是放弃其他功能；最终MVP范围仍需细化。

- **A · 语音听写优先（推荐）**：用户按键说话，文字提交到明确的外部应用目标。收益是直接验证效率工具价值，且不要求每次听写都通过LLM；难点是目标绑定、焦点变化、IME/富文本、原文保护与受限权限。初期支持明确应用集合，不承诺任意应用。
- **B · 角色语音聊天优先**：语音/文字与角色对话，有人设、状态反馈与朗读。收益是更快形成完整桌宠体验；ASR、模型和TTS链路都要配置，暂不直接解决跨应用输入或电脑操作。
- **C · 屏幕理解与受控操作优先**：围绕少量明确任务，完成读屏、确认后动作与回读。最接近帮忙办事，但权限、定位、敏感动作与失败恢复最复杂，不以任意自主操作作为首版承诺。

基础桌宠、设置和插件机制以支撑所选闭环的最小范围实现；不是先开发全部平台再寻找日常用途。若选择C，仍应分只读观察与有副作用执行两步验收。

## 已回答 Q12：听写怎样开始和结束？

状态：2026-10-24，用户选择C（一个键两种用法）。按下立即录音；长按松开即结束；轻点进入持续听写，再按一次结束。持续听写配静音自动结束与明显录音标识；需要能收到按键松开事件的键盘钩子。

- **A · 按住说话**：按住热键说话，松开即结束并识别。最直接、不易误触，适合短句；长段口述要一直按着。需要能收到“松开”事件的键盘钩子（Electron全局快捷键没有松开回调，见[技术预研](16-technical-recommendations-prep.md)）。
- **B · 按一下开始、再按一下结束**：适合长段口述，手不用一直按着；用Electron全局快捷键即可实现。风险是忘记结束会一直录音，需要静音自动结束和明显的录音标识。
- **C · 一个键两种用法（推荐）**：按下立即开始录音；按得久、松开即结束；只轻点一下则进入持续听写，再按一次结束。兼顾短句与长段，开始录音不需要等待判断。代价是需要键盘钩子、轻点与长按的时长阈值调校和误判处理。

默认热键、时长阈值、静音自动结束时长等数值，后续在交互细节中确定。
