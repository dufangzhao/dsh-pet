# QQ 接入

QQ 官方机器人和 OneBot 是同一个 Agent 的两个可独立启停入口。它们沿用服务的人设、State、任务和权限，不另建一套聊天代理。Web 管理配置与投递；桌面只显示状态，并提供「打开 Web 管理」。

当前实现选定 **QQ 官方生产 WebSocket** 和 **OneBot v11 反向 Universal WebSocket，SnowLuma 文件流扩展**。受控验收使用本地协议端、实际 Core/SQLite、编解码器和隔离执行容器；它不代表某个真实 QQ 账号、已安装 SnowLuma 版本或收件设备已经验证。首次上线仍需核对实际版本、账号权限和接收对象。

## 从独立数据根启动

按[服务启动与部署指南](35-text-agent-foundation.md)运行，使用明确的持久数据目录。已有服务的数据不自动迁入。两个 QQ 协议默认停用，名单默认空；保存配置不会试发消息或调用模型。

用服务令牌打开 Web，然后进入「QQ」。页面分别显示已保存配置、实际应用修订、连接阶段和清理状态。**已保存不等于已连接**；来源仍在退役或清理失败时，不能把新配置当成正在使用的连接。

## 配置协议来源

### 官方 QQ

1. 填写官方机器人 AppID，保存来源设置。
2. 通过受控本机入口填写该机器人的 AppSecret。
3. 为此 AppID 配置允许的私聊身份和群，再启用官方来源。
4. 私聊使用 `user_openid`，群内成员使用 `member_openid`，群使用 `group_openid`。它们不是普通 QQ 数字号，也不根据昵称或群主标签获得管理权限。

普通群消息需要平台及群主允许接收全量消息；只收到 @ 事件时，不能假称已经读取了完整群聊上下文。官方 WebSocket 连接本身不要求为消息回调开放公网 HTTP 地址。

### OneBot

1. 填写机器人自己的 QQ 账号，设置监听主机、端口与路径。默认是 `127.0.0.1:6199/ws`。
2. 保存来源设置，在本机入口写入独立 access token。
3. 在已安装的协议端配置反向 WebSocket、Universal 通道，以及相同 token。协议端连接本服务的监听端点；HTTP 管理端口与这个端口是两回事。
4. 配置允许的私聊 QQ 号与群号，再启用来源。

`127.0.0.1` 只适合同机访问；绑定全部网卡时，应向协议端提供实际可达的服务主机地址，不能把 `0.0.0.0` 当作连接地址。端点提示只描述配置，不证明网络或鉴权已通。当前不提供 forward/split 通道、任意扩展协议回退，或临时私聊会话自动转好友私聊。

文件传输依赖选定的 SnowLuma 扩展，不能推断任意 OneBot v11 实现都兼容。反向连接、流式文件动作及实际版本的核对依据见[协议研究](../.trellis/tasks/archive/2026-11/11-12-qq-platform-entry/research/onebot-environment.md)。

## 身份、名单与公开记忆

名单属于完整的协议来源和机器人账号。两个来源里同号的用户或群是两个身份，编辑一个来源不会迁移另一个来源的名单。

默认获准成员可对话、读取当前可见材料，并管理自己发起的工作。明确的主体别名可将外部身份绑定到同一个人；绑定为 `owner` 会关联个人助手的私有身份。群内仍使用群的受众范围，管理角色不会把私人聊天历史自动带进群。

管理员主体名单、主体别名和已知机器人身份都由 Web 操作者明确设置。平台昵称、QQ 群主/管理员标签、引用别人的话，以及知道一个任务 ID，都不授予这些权限。自己的消息和已知机器人消息不会被当成新的人类指令。

长期事实仍需明确写入。私人、群内和公开事实按范围区分，同一个 key 可以在不同范围共存。Web 可明确创建公开事实，或为已有事实创建公开副本；这不会悄悄删除原来的私人/群内记录。QQ 中的一般成员不能写长期事实，引用和历史观察也不充当记忆指令。

## 群上下文与主动参与

全局默认与每群覆盖使用同一组设置：@、唤醒词、近期消息条数/时长，以及主动参与策略。上下文先按身份和群过滤，再取窗口；设为零会排除旧群历史，当前消息、当前材料和明确引用资料仍可处理。

主动参与默认关闭。开启后可选择规则/概率，或在规则/概率之后再用独立模型判断。判断只决定是否参与，不授予成员权限、不创建新工作，也不直接替主 Agent 生成正式回复。

判断模型有自己的网关地址、模型标识、鉴权和凭据槽。先保存连接，再向那个已保存目标写入 Key；切换目标、连接或身份后，旧 Key 草稿不能借用新版本继续提交。它与前台模型的选择、密钥和退休过程相互独立。双 CAS 保存若只完成一部分，页面会重新读取实际状态并保留草稿，不能把错误响应解释成全部未写入。

## 文字、图片、语音与文件

文字始终保留。较长回复会以可见说明加完整 UTF-8 文本文件发送；Web 的「查看全文」与下载读取真实材料正文，不把说明文字当全文。多个正式回复段按原顺序组成一个投递批次。

图片和文件先取得并验证实际字节，模型与工作只能使用获准的材料引用。群文件通知没有真实消息身份时只作为可见资源；随后明确的请求可加载它，不会凭文件 ID 伪造一条人类输入。

QQ 语音输入复用[语音识别提供者](38-shared-voice-input.md)。先验证音频实际格式和时长，再完整识别；平台参考转写不自动代替这一步。引用语音的转写作为资料，不混进本次作者的记忆指令。

在 QQ 设置中打开「额外发送语音」后，只有本批必需文字已被平台明确接受，才会调用[语音输出提供者](39-shared-speech-output.md)并编码 SILK。QQ 声音不依赖桌宠在线或桌宠播放开关。文字失败或结果未知时不开始收费合成；语音失败保留已发送文字。原音频产物可作为文件发送，直接转发任意已收到的语音材料并不自动改成语音条。

编解码使用[固定 codec 插件与构建说明](../plugins/qq-media-codec/README.md)，当前选择 Linux amd64 Docker 镜像。服务读取其固定 image/manifest pin，实际使用前检查；缺镜像、来源停用或资源限制不满足时报告不可用，不自动拉镜像或借宿主 PATH 转码。

## 常用预算

| 项目 | 当前应用预算 |
| --- | --- |
| 近期群历史 | 每群最多30条、30分钟、12KiB完整历史记录；可配置得更小 |
| 等待输入 | 全局16、同受众4；默认2个输入上下文，硬上限4 |
| 输入材料 | 最多4份，单图8MiB，输入实际总量32MiB |
| 媒体准备 | 最多2个实际准备生命周期，staging总量128MiB |
| 语音输入 | 完整最多120秒；最多6个不重叠的20秒 ASR 段，转写总量8000 UTF-16单位 |
| 完整回复材料 | 最多64KiB UTF-8；QQ inline每段最多1024 UTF-16单位、最多两段 |
| 主动参与 | 默认关闭；默认每群60秒冷却、每小时最多6次逻辑回复 |
| 判断模型 | 全局单并发、每小时最多30次、默认每群60秒间隔、10秒截止、最多256输出 token |
| 官方被动回复 | 保守采用5分钟、C2C最多4条/群最多5条；同一原生消息的多个工作结果共用额度 |

这些是本应用的选择，不是所有 QQ 账号或协议端的统一平台保证。完整材料与来源元数据共同受记录预算限制，超限会明确拒绝，不裁掉正文后报告成功。

## 密钥与部署

QQ AppSecret、OneBot token 和判断 Key 使用独立的进程内凭据槽，不从 DSH、AstrBot、前台模型或其它提供者复制。当前进程重启后须重新提供；它们不写入聊天、Config 或 State。配置和启用意图则正常持久化。

密钥写入口只接受受信的本机 peer/Host/Origin。远程管理可通过 SSH 转发到本机入口后填写，不能把页面中的 `writable:false` 当作可写。反向代理应按[部署模板](deploy/companion.Caddyfile.example)阻断所有 credential 写入口；QQ 反向连接 token 与 Agent Web 访问令牌是不同凭据。

完整备份覆盖整个独立数据根，包括配置、SQLite、已保留工作产物和宿主材料。升级旧 State 格式时必须停服务，走已有冷迁移并保留完整备份；不会重放历史 QQ 输入、未知投递或过去的语音。

## 看懂投递结果

「已准备」「已上传/传到协议端」「平台接受消息」是不同事实，均不证明用户已阅读或听到。投递详情保留每段、每次操作和实际原生回执；未知结果不自动重发，也不改投另一个 QQ 来源或改成主动消息。

关闭单个协议连接不会取消已经接受的后台工作。工作结果保留原主体、受众和逻辑路由；来源离线、权限撤销或官方被动窗口过期时，结果仍可保留在 State，QQ 投递明确失败/阻止。清理未确认时不会把旧来源当作已成功退出。
