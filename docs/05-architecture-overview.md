## 分层建议

```text
用户
 ├─ 桌宠界面 / 气泡 / 快捷操作
 └─ 设置台 / 任务面板 / 插件界面贡献点
          ↓ 用户意图、配置、取消       ↑ 状态、结果、错误
产品工作流：聊天 / 听写 / 朗读 / 问屏幕 / 执行任务（范围待MVP确认）
          ↓ 通过能力契约，而非导入具体供应商实现
宿主内核
 ├─ 插件发现、依赖与生命周期
 ├─ 能力注册、协商与路由
 ├─ 任务标识、状态、流控与取消
 ├─ 配置、凭据代理与权限裁决
 ├─ UI贡献点注册与清理
 └─ 诊断、审计与资源状态
          ↓ 受控调用和媒体通道
能力提供者
 ├─ 音频采集 / VAD / ASR
 ├─ TTS / 音色制作 / 播放
 ├─ 形象导入 / 渲染 / 人设
 ├─ 屏幕采集 / OCR或VLM
 ├─ 文字注入 / 电脑动作 / 浏览器动作
 └─ 模型 / Agent / 记忆 / 可选DSH桥接
          ↓
操作系统、本地模型进程或授权云服务
```

以上是职责/数据流图，不是插件等级图，也不是已经选择的进程图。用户提出单层统一插件模型，职责通过能力依赖协作；具体语言、进程、传输与隔离仍需决策，参见[统一插件模型草案](11-plugin-composition-and-lifecycle.md)。

## 内核负责什么，不负责什么

| 内核负责 | 不应固化在内核中的业务 |
| --- | --- |
| 发现/启停插件、检查依赖、追踪资源所有权 | 某个ASR模型或TTS供应商的算法 |
| 选择可用能力、锁定一次任务使用的提供者 | 某个角色的专属动画与台词 |
| 统一任务、错误、取消和流控 | 每种应用或网页的专用自动化步骤 |
| 决定调用是否获授权、代理凭据 | 让模型输出直接决定自己的权限 |
| 提供稳定界面贡献点 | 任由扩展修改主界面结构/全局样式 |
| 配置迁移与诊断 | 在主线程下载权重或进行长时间推理 |

不要做“什么都能传的any消息总线”，也不要为了统一而抹掉音频、文本、图像和动作的能力差异。

## 工作流示例（候选功能，尚未全部纳入MVP）

### 直接听写

音频采集 → ASR → 文本/修订结果 → 目标确认与文字提交。

不要求LLM参与。可选润色应是明确功能而非默默改写用户原话；输入目标和权限由专门模块负责，不属于识别器。

### 语音聊天

音频采集 → ASR → Agent/模型 → 文本结果 → TTS → 播放；界面只消费状态/文本/表情事件。

若选端到端语音模型，提供独立实时会话能力，不能假装所有提供方都具有同样的分段/打断语义。

### 只读看屏幕

用户选择窗口/区域 → 获取带时间与坐标信息的观察 → 图像模型理解 → 回答。

读屏权限与输入执行权限分别管理；旧截图不能直接作为当前动作坐标依据。

### 受控电脑任务

用户目标 → 观察 → 动作候选 → 权限/目标校验与必要确认 → 执行 → 回读验证 → 下一步或结束。

模型只提出候选。退出、取消或授权撤回后不得继续发起新动作；已完成的外部副作用不能谎称可自动撤销。

## 插件间依赖原则（建议）

1. 依赖能力契约，不直接导入另一个插件的实现代码或读其私有文件。
2. 声明能力差异：流式、语言、离线、打断、声音设计等；不支持时明确失败或经用户接受后降级。
3. 一次任务记录选定提供者与配置版本，避免运行中修改默认提供者导致音频/文本乱序。
4. 资源和事件归属到插件/任务：停用时释放麦克风、模型会话、计时器、热键和面板。
5. 安装、加载、启用、授权是不同状态。不能因为已安装就自动运行高权限代码。
6. 受信任进程内插件、隔离脚本和原生进程的安全属性不同，后续明确支持范围；独立进程本身不等于OS沙箱。

## 交互与性能原则（建议）

- 本地输入反馈与远程结果解耦，处理期间仍能拖拽、停止、查看设置。
- 音频/图像采用专用有界流或引用，不向全局总线无限广播大块数据。
- 更新可合并、队列有背压、晚到结果可识别；取消覆盖整条所属链路。
- 不活跃的角色/面板/模型按需求降频、暂停或卸载；资源上限和阈值后续量化。
- 冷启动、持续运行、并行插件和GPU争用分别测量，不用单个平均耗时代表“丝滑”。
