# Shared desktop entry: next-stage research

Research only, 2026-11-08. Based on the current working sources; the parent is closing the model-text child after its separately recorded real-provider acceptance. No product edits, service starts, browser/model calls or data migration were performed here.

## Recommendation

Make the existing Electron pet and console clients of the already independent companion service. One Main-owned connection supplies both windows; the service remains the only Agent, message/fact/task/artifact and model-configuration authority. Retain the desktop host for local presentation, plugin permissions, appearance and existing audio mechanisms. Do not instantiate the legacy Cortico in the shared-client composition, including during disconnect or recovery.

This implements the approved second stage, not another architecture choice: [parent PRD R20](../prd.md#L31), [ADR-0015](../../../../docs/adr/0015-independent-continuous-agent-runtime.md#L9), [ADR-0016](../../../../docs/adr/0016-cloud-service-and-pluggable-features.md#L19). The [service guide](../../../../docs/35-text-agent-foundation.md#L64) and [service/model specs](../../../spec/backend/companion-service.md#L20) remain canonical contracts; this report identifies only desktop integration work.

Default scope: one explicitly configured service URL, one private owner using the current bearer token, text chat from console and pet, recent work/results, targeted stop and authenticated download, truthful connection/identity/persona visibility. Keep persona editing and semantic memory for the following child. No local execution daemon, transport framework, automatic legacy import, voice input integration or Live2D/platform overhaul.

- The browser [ModelDialog](../../../../plugins/text-client/src/client/model.tsx#L44) and [task strip](../../../../plugins/text-client/src/client/tasks.tsx#L20) are useful behavior precedents. 5. **Lifecycle and native acceptance (GPT integration + DeepSeek UI).** Exercise one real independent service with two actual surfaces, then disconnect/quit/restart desktop while work continues. ## Connection, token and effect lifetime

- Default service endpoint is a nonsecret suggestion, not discovery. Accept HTTPS, or exact loopback HTTP for local/SSH use; reject userinfo/query/fragment and unselected paths. Nonloopback plaintext HTTP is outside this default. Never forward the token across redirects or to a URL passed by a renderer/download response.
- Default token lifetime is this Main process/explicit connection only. The console supplies it once through the trusted bridge; clear its input immediately. Pet gets connection state, not token management. No token in Config, argv, logs, web storage, URL or public snapshots. Remembering a token across launches is unnecessary for this stage; existing encrypted storage can be a later explicit convenience.
- Bind all requests, SSE readers and optional persona/model forms to `{source owner generation, config revision, normalized endpoint, connection generation}`. Snapshot refreshes/commands/downloads from retired generations cannot publish into the replacement, clear its drafts or confirm another command. Clear the old token and pending target-bound intents when explicitly changing service/auth; uncertain intents can only retry against the same admitted target and identity. Reconnect same target reconciles a fresh snapshot/epoch; a changed Agent ID is visible, not silently merged.
- Disconnect/disable/revoke/quit aborts and actually drains local network readers/downloads and fences callbacks. Recheck source fingerprint at admission, delivered frame and return boundaries; explicit revoke aborts live authority. Match existing semantics: no filesystem watcher or instantaneous disk-change claim. Unknown cleanup is unavailable/pending_restart, not proof of a clean replacement.
- Local disconnect never posts service stop. HTTP cancellation does not retract an already accepted message/task; keep unknown outcome until same-ID retry or snapshot confirmation. Offline retains last confirmed content and timestamp; nonterminal tasks/status become stale/unknown and mutating service controls are unavailable. Keep local drag, appearance and playback stop working.
- Artifact save is authenticated fetch in Main, then a native user-selected save destination, bounded/abortable transfer and fixed error result. IPC takes an artifact ID from the current projection, not an arbitrary URL/path. Do not buffer arbitrary file bytes through JSON IPC or put bearer tokens in `shell.openExternal`/download URLs.
- Keep stop scopes distinct: immediate local playback stop, foreground generation stop and a selected background task stop. [Current console stop-all](../../../../apps/desktop/src/main/index.ts#L500) and tray stop cancel local supervisor work; relabel them as local or replace their shared affordance. The [old pause action](../../../../apps/desktop/src/main/application-controller.ts#L227) has no equivalent durable service pause. Disconnect is not pause.
- Native Main must not become a credential-ingress proxy. The service [gateway-key route](../../../../apps/companion-service/src/server.ts#L370) is deliberately local-only. Default shared desktop does not relay `/api/model/credential`; model save/test may use the existing APIs, while independent gateway key provisioning remains with the service operator. Project its writable flag accordingly. Never forward desktop/DSH legacy keys to the service.
- Reconnection projects text and tasks only; it must not replay speech, touch actions, historical dialogs or old device effects. Default auto-speech remains disconnected from remote catch-up; explicit local playback remains available. Future live-output policy must distinguish initial/catch-up state from new delivery rather than treating every snapshot difference as audible output.

## Execution environment follow-up: Linux is not the Windows desktop gate

Read-only host checks on2026-11-08 established `linux-x64`, kernel5.15, glibc2.35 and Node26.13.0. `DISPLAY`, `WAYLAND_DISPLAY` and `XDG_RUNTIME_DIR` are absent; `/tmp/.X11-unix` is empty. `Xvfb`, `xvfb-run`, `Xorg` and `weston` are not on PATH. The installed Electron45.0.0 npm package has neither `path.txt` nor `dist/`; no executable was available at its expected package location. A separately provisioned binary/display could be supplied later, but none was verified here. Existing Linux headless Chromium browser tooling does not supply an Electron Main/preload runtime or an X server.

Research incident: evaluating `require('electron')` to obtain its path unexpectedly triggered the package's auto-downloader. The [installed entry](../../../../node_modules/electron/index.js#L25) executes its installer when the binary is missing. The command was cancelled; the tracked job ended with SIGTERM, and a subsequent process/filesystem check found no Electron installer process and still no `dist/`. No Electron application, build or acceptance probe was run. Future preflight must inspect files/metadata without requiring this package entry; this interrupted attempt is not successful provisioning or native acceptance evidence.

### Minimum legitimate Linux native composition

Implement a dedicated QA entry for the **new shared text client**, not a pretend Windows launch of the old application. It should compose the same production Main connection controller, request validators, preload bridge and production shared pet/console text views developed by the child. Use actual Linux Electron BrowserWindows, existing window factories where applicable, local file URLs and unchanged sandbox/contextIsolation/CSP checks. Reuse pure drawing/composer/shell components directly; do not duplicate their implementation or replace `window.petCompanion` with an in-renderer mock.

Mount only the new client source whose real manifest explicitly supports linux-x64 and win32-x64. Use the existing kernel/SDK/ConfigService/permission/task primitives with actual `linux-x64`; retain source verification, declared token/config access, deny/revoke and drain behavior. A narrow QA composition can build these primitives directly without the legacy DesktopHost's hardcoded target. Do not create another plugin framework. If the production shared host itself must run on Linux, let that host select the actual supported platform rather than adding a “pretend platform” option; all unchanged Windows-only packages must still be rejected. Existing profile/avatar/page plugins are not silently added to the Linux test set. Their future real Linux support would require an explicit bounded manifest/source review and acceptance, not bulk editing every manifest.

This composition may use fixed presentation inputs for unsupported local settings, clearly labeled QA-only; its service chat/tasks/downloads must be real. The Linux native pass then proves the new client plus reused text UI and Main bridge. It does **not** prove the unchanged Windows application, legacy-profile integration, Windows avatar plugin activation or all local device behavior. Keep a separate Windows shared-startup gate for old-profile preservation, real page admission and prevention of legacy Core/OAuth/voice restore. This is a verification split, not two canonical Agents or an alternative product direction.

### Executable acceptance path for the next child

The following is a proposed runner contract; `qa/probes/companion-desktop-native.mjs` does not exist yet. Implement it with the child, then run only after its Electron/display prerequisites are deliberately provisioned. No provisioning, build or launch command was executed in this follow-up.

1. **Preflight without downloads:** read Electron package metadata via `require.resolve('electron/package.json')`, inspect its `path.txt` and expected binary with filesystem APIs, and fail immediately if missing. Accept a verified absolute `COMPANION_ELECTRON` executable override. Check real host platform/arch, binary shared-library availability (`ldd` after the binary exists) and an explicitly supplied X11 display or Xvfb. Forward `DISPLAY`, `XAUTHORITY`, `HOME`, `XDG_RUNTIME_DIR` and any operator-provided library/font variables to the launched Electron; do not reuse the old Windows-only env list. Clear `ELECTRON_RUN_AS_NODE` for the Main launch. Missing prerequisites produce an explicit not-run report, never a passed/skipped Windows gate.
2. **Build once under the child's normal quality gate**, including production bridge/views and the narrow QA Main entry. Start a temporary independent service on loopback ephemeral port with isolated durable data and a controlled model peer/scripted mode; no host4120 or paid-model dependency. Start a separate normal browser against that same service for the second surface. Keep its temporary token inside runner memory/connection files with owner-only permissions; never argv/report screenshots.
3. **Launch the Linux native runner under provisioned X11/Xvfb**, for example the command below. It uses Playwright `_electron.launch({executablePath: process.env.COMPANION_ELECTRON, args:['--no-sandbox', <built-QA-main>], env:<explicit-display-env>})`, not Chromium's browser launcher. Report actual `process.platform`, Electron/Node versions, build hashes, both loaded file URLs, security preferences and visible pet/console windows. `--no-sandbox` is the existing controlled QA exception and gives no OS-sandbox proof.

```sh
# Future runner, after build and deliberate Electron/Xvfb provisioning:
COMPANION_ELECTRON=/absolute/provisioned/electron \
  xvfb-run -a -s '-screen 0 1440x1000x24' \
  node qa/probes/companion-desktop-native.mjs
```

4. **Drive real DOM actions** in both Electron windows: enter URL/token, send once from the pet, observe identical durable IDs/messages in console/browser, start two service tasks, stop only one, disconnect/close/relaunch desktop, and retrieve the completed artifact through the Main save path with byte/hash verification. Cover auth refusal, ended SSE, uncertain same-ID resend, source revoke/disable and late-target replies. Check that no renderer makes HTTP requests or receives the stored token. Resize console to880×600 and exercise keyboard/dialog focus. Use the real native save dialog, or clearly label a deterministic host-owned destination test as download-transport evidence and keep actual dialog acceptance pending.
5. **Keep reports scoped:** Linux proves actual Electron rendering, trusted IPC/Main HTTP/SSE/task/download paths and ordinary new-client lifecycle. Node HTTP/browser tests alone prove no Electron bridge. Windows execution remains the authoritative gate for unchanged legacy package integration, OS pointer effects and Windows-device features; voice/keys are explicitly outside this child. If no Linux Electron/display or Windows runner can be provisioned, implementation and nonnative checks may proceed, but native acceptance remains pending with these concrete prerequisites.
