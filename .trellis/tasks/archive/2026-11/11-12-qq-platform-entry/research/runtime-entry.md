# Runtime entry research for QQ plugins

Recorded 2026-11-12 against HEAD `b706007`, branch `feat/qq-platform-entry`. This is a source-backed planning note, not implementation approval. Product files were not changed; no service, account, message, test or live inference was run. AstrBot/protocol findings belong to the separate upstream research.

## Conclusion

Reuse the existing single `CompanionRuntime`, canonical State, selected Harness and independent workers. QQ adapters can be ordinary replaceable plugins. Multiple people/private chats/groups nevertheless require more than forwarding text to `/api/messages`: canonical provenance/audience, participant authority, task-result routing and platform delivery facts have real gaps.

Do not introduce an Agent, memory database or user-managed Session per platform/group. Shared Agent identity does not imply that every participant may read private context or exercise owner authority.

## Verified current contracts

### Input and identity

- `CompanionMessageCommand` contains only `{commandId,text}`; State rejects extra fields. There is no platform, sender, conversation or reply-target field. See [command DTO](../../../../../../packages/contracts/src/companion.ts#L129) and [input validation](../../../../../../plugins/state-sqlite/src/validation.ts#L101).
- `runtime.message` checks interaction availability, looks up the exact original command, reserves any memory admission, commits `acceptMessage`, then calls Harness `accept`. A known duplicate does not redeliver to the Harness. If storage succeeds but Harness admission fails, runtime appends a notice and reports failure; a new command ID must not be invented to hide that uncertainty. See [message admission](../../../../../../packages/companion-runtime/src/runtime.ts#L652).
- `acceptMessage` generates canonical user-message `id`, records the caller's `commandId` as that user's `inputId`, and atomically stores its receipt/event. Harness receives the canonical message ID. See [State acceptance](../../../../../../plugins/state-sqlite/src/state.ts#L382).

| Identifier | Current meaning |
| --- | --- |
| Submission `commandId` | One intent; same ID/payload deduplicates, changed payload conflicts |
| User message `id` | Canonical UUID generated by State |
| User message `inputId` | Original submission `commandId` |
| Harness user input `id` | Canonical user message `id` |
| Assistant reply to a user: `inputId` | Canonical user message `id` |
| Assistant reply to work completion: `inputId` | Synthetic `work-event-<executionId>`, not necessarily a messages row |
| Product `taskId`, `executionId`, supervisor task ID, native Session ID | Distinct identities; none is a platform conversation ID |

The work-result notice uses `work-result-<executionId>`, while the Harness input uses `work-event-<executionId>` and carries the product `taskId`. See [work completion publication](../../../../../../packages/companion-runtime/src/runtime.ts#L873).

### Formal assistant publication and attribution

- `say(inputId,text)` validates that the input belongs to the current model round, awaits publication and then returns `Reply committed`. Multiple different `say` outputs in one turn are separate formal assistant messages. Their IDs hash input IDs and text, so identical text for the same inputs deduplicates. See [output identity](../../../../../../plugins/harness-cortico/src/harness.mjs#L100) and [tool admission/publication](../../../../../../plugins/harness-cortico/src/harness.mjs#L173).
- Complete ordinary assistant text without a function call is also published at `onRoundEnd`, using **all** round inputs. `outputFor` supplies a `taskId` only for a single input. The runtime then persists **only `output.inputIds[0]`**. Thus a response involving multiple input sources loses attribution; this is especially consequential when those sources have different audiences. See [ordinary-text publication](../../../../../../plugins/harness-cortico/src/harness.mjs#L319) and [runtime publication](../../../../../../packages/companion-runtime/src/runtime.ts#L1040).
- `startWork` receives an origin containing input IDs, but runtime retains only `origin.id` as the task command ID. The durable task has no originating input, actor or audience. See [startWork port](../../../../../../packages/companion-runtime/src/runtime.ts#L1054), [task DTO](../../../../../../packages/contracts/src/companion.ts#L34) and [task writer](../../../../../../plugins/state-sqlite/src/state.ts#L435).
- `finishInputs` releases delivered inputs' temporary memory admissions; it is not a reply-complete or platform-delivery acknowledgement. See [runtime release](../../../../../../packages/companion-runtime/src/runtime.ts#L976).
- Reusable output source: committed message events plus `getMessage({id,eventSequence})`, followed by an assistant-role check. Events carry IDs/role, not reply text. The lookup verifies the exact event/message pair. Snapshot differences and model deltas are unsuitable delivery feeds. See [message event writer](../../../../../../plugins/state-sqlite/src/state.ts#L405), [canonical lookup](../../../../../../plugins/state-sqlite/src/state.ts#L264) and [M5 contract](../../../../../spec/backend/shared-speech-output.md#L29).

### Shared identity, context and work

- State owns one persistent `assistantId`; runtime projects that ID. Core Config owns the common persona/Harness selection. Cortico declares one foreground Session, whose history is a disposable projection. See [persistent identity](../../../../../../plugins/state-sqlite/src/state.ts#L83), [Agent snapshot](../../../../../../packages/companion-runtime/src/runtime.ts#L607) and [foreground declaration](../../../../../../plugins/harness-cortico/src/harness.mjs#L319).
- Interaction admission does not reject merely because the Agent is busy. Inputs arrive through `pushEvent(...,{trigger:'flush'})`; delivered inputs become eligible for subsequent inference. Long work has a separate supervised root and returns acceptance before completion; foreground cancellation does not cross the `startWork` port. See [interaction availability](../../../../../../packages/companion-runtime/src/runtime.ts#L642), [event submission](../../../../../../plugins/harness-cortico/src/harness.mjs#L417), [task admission](../../../../../../packages/companion-runtime/src/runtime.ts#L727) and [independent-root boundary](../../../../../../plugins/harness-cortico/src/harness.mjs#L194).
- Context currently includes active facts and recent messages/tasks without participant/audience filtering. The existing single foreground is not evidence of multi-party fairness or privacy isolation. See [context projection](../../../../../../plugins/harness-cortico/src/harness.mjs#L32).

Important limits:

- Headless readiness currently accepts only capability-use/files/process/credentials; a network declaration is unavailable. Its SDK port does not inject `withSecret`. `hostCredentials` is a private transport key allowlist, not a credential value or generic network grant. See [readiness](../../../../../../packages/companion-runtime/src/plugin-host.ts#L293) and [SDK port construction](../../../../../../packages/companion-runtime/src/plugin-host.ts#L199). Existing service transports use host-private CredentialBroker borrowing with a memory store, not a new persistent secret store; see [transport example](../../../../../../apps/companion-service/src/speech-client.ts#L29).
- `host.owner/runFor` requires an active source. Activation can register/bind, but source-authorized connection work must begin after activation. See [owner check](../../../../../../packages/companion-runtime/src/plugin-host.ts#L399) and [runFor](../../../../../../packages/companion-runtime/src/plugin-host.ts#L508).
- Platform disconnect must retire only its connection resources. `runtime.close()` stops the Harness and cancels shared work. Service shutdown should retire the new entry before the runtime, through the existing cleanup chain. See [runtime shutdown](../../../../../../packages/companion-runtime/src/runtime.ts#L1251) and [service cleanup](../../../../../../apps/companion-service/src/service.ts#L161).

## Actual contract gaps for multi-party QQ

1. **Canonical provenance:** no adapter/account/external-message/participant/conversation/reply-target fields. Text prefixes are neither identities nor authority. Required provenance should survive acceptance/restart rather than live only in an adapter Map.
2. **Reply and task routing:** multi-input ordinary output is collapsed to the first input; task origin is discarded. Late results cannot reliably recover their original external audience. Do not route by the latest contact or broadcast a multi-input answer.
3. **Participant authority and visibility:** HTTP uses one operator bearer. After admission, routes include profile/fact/task/plugin operations. Natural memory cues give all admitted messages the same memory-admission mechanism; Harness only distinguishes user/work-result, and `stopWork` receives no participant origin. Owner bearer authorization is **not QQ sender authorization**. See [HTTP authority](../../../../../../apps/companion-service/src/server.ts#L305), [mutation routes](../../../../../../apps/companion-service/src/server.ts#L400), [memory admission](../../../../../../packages/companion-runtime/src/runtime.ts#L665) and [stopWork port](../../../../../../packages/companion-runtime/src/runtime.ts#L1058).
4. **External delivery facts:** canonical command/message/event commitment proves no platform send. There is no platform message receipt or unknown-send reconciliation contract. M5's future-only baseline is a Pet playback decision, not an already-selected QQ reconnect policy.
5. **Composition and transport:** the ordinary plugin mechanism exists, but a platform factory, narrow ingress/output port and source-bound connection transport are missing. Multiple accounts for one plugin or runtime hot installation would additionally exceed the present service composition; address those only if selected.

## Minimal candidate slice — recommendations, not decisions

- Keep official QQ and OneBot protocol modules independently replaceable. Each owns protocol translation and connection resources, not Core/persona/memory/work scheduling.
- Add a narrow source-bound host port: admit verified external inputs, expose authorized committed assistant output, and perform target-bound transport operations. Do not hand an adapter the operator bearer or unrestricted runtime management methods.
- Extend canonical input/message/task provenance only as required by the chosen audience scope. Preserve command deduplication and State transaction ownership. Host-derived participant authority must also reach tool admission/context selection; model text cannot assert it.
- Retain one Agent and shared canonical state. Conversation IDs are provenance/audience/context-selection dimensions. Define how a formal output acquires an authorized audience when more than one input source participates in a round.
- Store only necessary nonsecret transport configuration, cursor/remote receipt/unknown-send facts. Keep credentials independently provisioned. Fence old config/key/connection bindings before fallible drain; enable replacements only after cleanup is confirmed. Do not create another conversation database or general platform framework.

## User decisions still open

The parent's immediate question is **official QQ first, OneBot first, or both in the first release**. Do not preselect this in implementation or interpret studying both as approval to build both.

After that choice, scope still needs to establish:

- Owner-only private chat, allowlisted people, specified groups, or combined use; whether channels, multiple accounts or media/files/voice are included.
- Group triggers: mention, quoted reply, explicit prefix/keyword or ordinary messages; whether non-triggering traffic enters context/history.
- Owner binding and other participants' rights: chat, memory writes, private fact reads, work creation, task inspection/cancellation. Group administration must not silently become Agent ownership.
- Private/group/desktop context visibility and the permitted audience of delayed task results; proactive notifications and reconnect catch-up behavior.
- Credential supply and restart recovery, and handling sends whose external outcome is unknown. Existing model/ASR/TTS credentials or consumed live-TTS authorization do not grant QQ access.

Candidate later acceptance anchors: group A's work continues while private chat B receives a response; all formal `say` messages and late results retain the correct audience; duplicate ingress/events do not duplicate effects; retired callbacks cannot send; stopping QQ does not stop shared work; nonowners cannot mutate private memory or stop unauthorized tasks. These are proposed checks, not executed evidence.
