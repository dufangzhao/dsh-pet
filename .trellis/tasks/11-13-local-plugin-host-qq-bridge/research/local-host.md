# Local QQ host and remote Agent bridge — source investigation

This is a planning investigation, not an implementation or test result. The [task PRD](../prd.md) is authoritative: **both** official QQ and OneBot adapters and their platform credentials/private upload references belong on the user's local host; the existing server remains the one Agent, State writer, policy owner and cloud-work authority. No current file provides this distributed bridge. In particular, M6's integrated service-side QQ adapters are not evidence that the requested deployment already works. No actual QQ account, paid model, original 4120 data, existing SnowLuma instance or test Agent was accessed for this investigation.

### The concrete QQ activation blocker

Both protocol manifests honestly declare `win32-x64` and Linux x64, own a source config and credential key: [official](../../../../plugins/qq-official/plugin.json#L1), [OneBot](../../../../plugins/qq-onebot/plugin.json#L1). However, their ordinary default exports intentionally fail closed: [official default](../../../../plugins/qq-official/src/index.ts#L51) and [OneBot default](../../../../plugins/qq-onebot/src/index.ts#L54). The actual `createOfficialQqPlugin(portsFor)` and `createOneBotQqPlugin(portsFor)` factories at those files' lines 16–48/16–50 need host-private functions, bind their real drivers and register physical cleanup. Today's [server composition](../../../../apps/companion-service/src/service.ts#L469) injects these closures directly into an in-process `CompanionPluginHost`/Cordis runtime; [QQController](../../../../apps/companion-service/src/qq-controller.ts#L704) supplies `authorizedOfficial`, observer, bind and exact source checks. Desktop's verified worker loader only sees the fail-closed defaults. Adding entries to `localRoles`, copying manifests, or reporting `describe` does not install the private port or start an authorized adapter.

There is also an actual host-interface mismatch. [createQqAuthority](../../../../apps/companion-service/src/qq-native-types.ts#L39) is currently typed to `CompanionPluginHost`, uses `verifySource`, `runFor`, source Config/generation checks, a memory-only credential binding and a source lease, and joins broker/native work at lines 101–171. `DesktopHost` owns equivalent primitives but has no identical `runFor`/`verifySource` API: it uses `tasks.run`, `describeTrust` and async `verifyTrust`. Extract a **narrow source-bound host port** or supply a checked adapter; do not instantiate `CompanionRuntime` or server State locally just to satisfy the type. Keep Config CAS and broker namespaces with the actual local plugin owner. Do not bypass the worker by sending its secret or raw host object through ordinary capability JSON.

## Independent-host decision and composition candidates

Accepted [ADR-0016](../../../../docs/adr/0016-cloud-service-and-pluggable-features.md#L9) already chooses cloud-eligible work surviving client disconnection and views being removable without deleting tasks. The user further selected on 2026-11-14 that QQ **must continue after explicitly exiting the desktop application**; [L11/A9](../prd.md#L21) therefore require an independently running local host and a separate stop action. Reuse the existing kernel, PluginManager and one-plugin model; this is not a second plugin standard.

| Candidate | What it reuses / changes | Consequence |
| --- | --- | --- |
| **A. Existing UI Desktop Main owns the local QQ source.** | Reuses `DesktopHost` and its permission UI, but the present Main quit sequence shuts it down. | **Does not satisfy L11/A9** when the desktop process exits. Hiding a window is different from exiting the process. |
| **B. Independent local host process** owns QQ and the bridge; desktop remains a client of that host and its separate existing Agent connection. | Reuse either the in-process `CompanionPluginHost`/Cordis composition or a headless `DesktopHost`/worker, both on the existing kernel/PluginManager, with explicit local source-control IPC. No local Core/State and no parallel owner for the same QQ instance. | Meets the selected lifecycle only after actual process, credential and cleanup proof. It adds a versioned process/single-instance boundary; the user did not thereby authorize automatic OS startup or an installer. |

### Can `CompanionPluginHost` be the minimal host?

**Static source facts:** [CompanionPluginHost.create](../../../../packages/companion-runtime/src/plugin-host.ts#L115) accepts a list of manifests and ordinary `PluginDefinition`s and constructs `CordisRuntimeDriver`, `PluginManager`, `ConfigService`, `PermissionKernel` and `TaskSupervisor` directly; it does **not** construct a `CompanionRuntime`, State provider, Core or server. `runFor(sourceId, ...)` uses that active source ([implementation](../../../../packages/companion-runtime/src/plugin-host.ts#L508)), and [withSourceAuthority](../../../../packages/companion-runtime/src/source-authority.ts#L6) needs only `runFor` and `permissions`. Thus a daemon can in principle register a small local bridge/source definition and the two QQ definitions, initially disabled; after creating a small local source controller, explicitly enable only configured sources. The actual QQ definitions must be created by `createOfficialQqPlugin(portsFor)` and `createOneBotQqPlugin(portsFor)` and supplied to the in-process loader. Their default exports still fail closed; no callback is magically injected.

**Necessary changes / limitations:** this is a feasible minimal *composition*, not a finished standalone host. The current [QQController](../../../../apps/companion-service/src/qq-controller.ts#L528) also depends on server `CompanionRuntime.profile`, policy/feature grant, State, judge and delivery. Extract or compose its source-only lifecycle/Config/CAS/key/observer/native binding portion against explicit local ports; do not fabricate those server dependencies. Existing `CompanionPluginHost.create` takes a fixed registration list, labels entries builtin, automatically confirms the supplied fingerprint and sets each supplied preset ([install loop](../../../../packages/companion-runtime/src/plugin-host.ts#L338)); it is not the desktop's reviewed user-package discovery, removal, permission UI or independent daemon singleton. Reuse the kernel's actual discovery/verification/approval and owner-scoped broker as appropriate for removable sources; do not silently treat every discovered source as trusted. Existing `createQqAuthority` has an in-memory broker and takes a secret already supplied by the host, not a persistent secret vault. The private native connection remains per-source and starts only after activation, captured checks and supervised source work. Whether an in-process loaded source has the intended integrity/isolation and actual Windows cleanup is a **Phase 0 proof**, not a claim based on this static read.

### Is headless `DesktopHost` cheaper?

[DesktopHost.create](../../../../apps/desktop/src/main/desktop-host.ts#L90) itself already composes verified discovery, Config/CAS, permission UI primitives, optional `CredentialBroker`, PluginManager, a worker and source cleanup; its shown constructor has no `CompanionRuntime` or State. A separately launched headless Electron main could instantiate it without creating pet/console windows. It still needs daemon-specific UI IPC and process lifecycle, source-only operations and a narrow bridge. Most importantly, its worker uses the fail-closed QQ defaults: merely enabling QQ cannot invoke the `portsFor` factories. It must either route only those verified sources through a specifically composed in-process Cordis driver, or add narrowly typed worker-side QQ source/observer/byte ports with owner/task/cleanup fencing. That extra integration makes it incorrect to call the existing worker a ready QQ host. Exact architecture and smaller actual diff are a Phase 0 comparison; both candidates use the same kernel and plugin lifecycle.

**Windows secret constraint:** the existing production [SecretCipher](../../../../packages/host-kernel/src/credentials/secret-cipher.ts#L1) explicitly takes Electron's asynchronous `safeStorage` and rejects non-Windows; desktop injects it after `app.whenReady` ([startup](../../../../apps/desktop/src/main/index.ts#L214)). A plain Node daemon has no injected Electron Main `safeStorage` in this code and there is no production Node DPAPI adapter shown; it can keep token/QQ keys in memory for its lifetime or needs a separately implemented and verified OS-backed `SecretCipher` for persistent storage. An Electron **main-process** host without windows can in principle inject the existing adapter; `ELECTRON_RUN_AS_NODE` worker mode is a Node process, not a demonstrated `safeStorage` provider. Test actual Windows user/session/profile behavior rather than assuming persistence or silently falling back to plaintext.

## Fixed bridge proposal and authority ownership

This is a narrow candidate, not an existing API or a generic remote plugin bus:

1. **Authenticate the independent host to the existing Agent.** The smallest first-personal-use candidate is the existing owner-supplied service bearer, carried only by the local host over the already selected TLS-protected Agent target to a new *closed* QQ bridge endpoint. The current server has one management bearer, not a bridge-only key; this reuses it honestly and does **not** provide narrower server credential privilege or separate per-device token revocation. The daemon owns the bearer privately, separate from the QQ plugin/worker and QQ platform secrets. The endpoint accepts only bounded QQ bridge messages, not generic RPC, arbitrary HTTP, shell or device calls. A party possessing the owner bearer already has the owner's current API authority; limiting this endpoint does not change that. Dedicated scoped credentials can be future work if the threat model requires them, not a prerequisite for inventing a PKI/pairing registry here. No token goes in URLs, renderer snapshots, State, logs or model context. Server attribution trusts the authenticated owner-controlled host to report the native account/actor; a JSON digest/role is not independent cryptographic proof.
2. **Separate logical identity from live authority.** Local Config owns official app ID/scenes or OneBot account/listener settings and the local credential slot; server keeps canonical policy and Agent state. Preserve the logical `QQAccountRef` for policy and deduplication, but separately bind this live source to the authenticated bridge session, protocol/source ID, local plugin owner generation and reviewed digest, local Config revision, credential version, permission epoch, a host-boot/session nonce and actual physical QQ peer ID. A generation by itself can repeat after process restart; account equality is not connection identity. Server-side attempt/provenance must retain the required old-source binding; a new connection/account must not satisfy an old attempt. A bounded current-source/session map, using or adapting existing source records, is necessary runtime state, not a new durable pairing registry or additional identity/persona/history database.
3. **Keep server grants server-private.** Local adapters parse protocol frames and emit a fixed, bounded, sanitized event DTO. The server validates its exact shape and registered source/account, derives actor, route and stable event key, checks current server policy/aliases/group settings, and issues the existing `RuntimeInputGrant` itself ([policy](../../../../apps/companion-service/src/qq-policy.ts#L21), [input authority](../../../../packages/companion-runtime/src/input-authority.ts#L21)). Neither a device-supplied role, owner flag, account string, media ID nor an opaque correlation is an authorization grant. Event dedup must use the stable logical native message/event basis, not a fresh bridge-connection nonce; rebinding the transport must not create another input.
4. **Replace only the local-source seams, not the Agent.** The server keeps `QQIngress` policy/admission, judgment, runtime dispatch, materials, tasks and frozen State ledger; its current concrete [source capture and `sourceFor`](../../../../apps/companion-service/src/qq-controller.ts#L661) assume an in-process controller and drivers and therefore need an explicit remote-source facade. Local code owns the actual protocol factories, `OfficialIo` / `OneBotIo`, local source task, QQ credentials, connection signals and physical cleanup. The server may request only the finite QQ operations for an already-authorized route/part, never arbitrary capability names, URLs, paths, sockets, executables or an operator-chosen host command.
5. **Do not couple participant grants to the bridge.** The source/bridge/physical-peer signal fences pending ingress/downloads and new native effects; the existing participant policy lease is separate and survives local transport or capability loss for already accepted cloud-eligible work ([input-authority](../../../../packages/companion-runtime/src/input-authority.ts#L21)). Server-side removal/downgrade of the actor or revocation of its participant permission is rechecked and sticky; reconnect cannot promote/revive that grant. Local source trust or permission withdrawal also remains sticky for the old local source generation and its device effects, but by itself does not revoke already accepted cloud work. That work completes under its original task/audience even while the local host is unavailable. Local effects remain unavailable until a newly authorized operation exists; no implicit re-targeting.

For an actual event received while disconnected, do not pretend it reached State. The official driver advances its sequence after the observer completes ([driver](../../../../plugins/qq-official/src/driver.ts#L293)); any resume behavior needs a bounded, failure-aware handoff and real platform behavior remains unverified. OneBot event delivery does not supply an invented durable acknowledgment or guaranteed replay. Bound any in-memory queue/backpressure and surface offline/loss rather than create another chat history or claim a platform guarantee.

## Minimal Agent-link, UI exit and exact target

**Static fact:** today's [desktop client](../../../../apps/desktop/src/main/companion-client-controller.ts#L200) owns its service token and HTTP/SSE connection in UI Main; its [withToken](../../../../apps/desktop/src/main/companion-client-host.ts#L126) borrows an in-memory supplied token, and explicit disconnect/process exit loses that binding. Current [desktop quit](../../../../apps/desktop/src/main/index.ts#L164) shuts down its host. Neither the present client connection nor the worker is an independent persistent QQ bridge. In fact [worker-entry](../../../../packages/host-kernel/src/runtime/worker-entry.ts#L135) shuts down on parent IPC disconnect, so detaching the existing worker and calling it a daemon would fail the selected exit requirement.

**Smallest proposed ownership:**

1. Start or attach to one independently running host for the current Windows user/profile through a fixed local endpoint; the daemon owns its own QQ-source Config/permission/task state and its own QQ bridge connection. Have an atomic singleton/endpoint ownership protocol, distinguish live from stale owner, and never start a second owner of the same source. The local endpoint exposes only explicit host status, start/stop/configure/credential and connect/disconnect actions; it is not generic RPC. Protect it with a verified same-user Windows named-pipe access boundary and a fresh host-boot identity; pipe squatting, process-death cleanup and actual ACL behavior require native proof, not assumed properties.
2. On an explicit owner connect/attach action, use the already supplied service token through a private one-shot authenticated local channel to the daemon, with the exact normalized service origin and expected Agent identity from the currently confirmed desktop snapshot. The daemon holds its own in-memory copy for its bridge lifetime. It independently verifies the server under TLS and verifies the returned canonical `agent.id` and State epoch before announcing a live QQ source; do not trust a URL/identity typed by a QQ plugin. Ordinary desktop close does not close this host link or erase the daemon's copy. Explicit host stop, target replacement, authorization failure/revocation or daemon exit fences/drains it; a daemon restart in this minimum memory-only design requires the owner to supply the token again. Persist only if an explicit, tested OS-backed cipher policy is adopted; no plaintext or hidden environment import.
3. The daemon may reconnect after transient loss **only** to the same captured endpoint and same expected Agent/epoch, with a new bridge-session nonce and freshly fenced source bindings. If identity/epoch or target changes, stop/reconcile the old source and require a fresh explicit owner action; do not silently follow the desktop to a different server or replay an unknown attempt. Server restart and legitimate epoch changes must be surfaced rather than guessed. An accepted cloud task remains with its original Agent regardless of UI/host loss.
4. On GUI reopen, attach to the existing daemon rather than launching another; show its actual target, Agent identity, host boot and source/bridge status. Compare those facts with the GUI's current server snapshot before presenting controls as applying to the same Agent. A mismatch is a distinct unavailable/target-mismatch state with an explicit reassignment flow; delayed replies carry the captured daemon/session/target rather than the latest GUI selection. Local source Config CAS and server policy CAS remain different owners.

The existing GUI `DesktopCompanionController` may continue independently using its normal owner HTTP/SSE connection and existing M4/M5 controls. The daemon has a separate long-lived, narrowly typed QQ bridge connection to the **same verified Agent**. One continuing Agent does not require one transport socket; it requires consistent exact target/identity and no second State authority. Adding the private token handoff/attach seam does not require proxying every existing voice/speech or other desktop API through the daemon.

An independent Electron-main host is a plausible Windows-first implementation because it can own `safeStorage`, but the present [single-instance lock](../../../../apps/desktop/src/main/index.ts#L188) and shared startup/quit sequence were built for one UI process. A role-aware daemon startup must avoid that UI lock collision and must remain alive without any window or parent-IPC lifetime; use independently owned process startup/stop, not the UI's current worker child. Test packaged process identity, named-pipe ACL and two real process lifetimes before claiming this works. A Node-based host is also possible if the memory-only token lifetime is acceptable or an actual secure OS cipher is provided; no database of users, CA, device-enrollment registry or invisible OS service is necessary for the first personal-use candidate.

## Media and native-reference boundary

Current M6 internals are **not safe to serialize directly across this new boundary**: [QQRemoteMaterial](../../../../apps/companion-service/src/qq-input.ts#L24) embeds official attachment URLs or OneBot segments, while [QQDeliveryOutcome](../../../../apps/companion-service/src/qq-delivery.ts#L49) may carry `uploaded` as native `file_info` or gateway staging state. [Official multipart](../../../../apps/companion-service/src/qq-official-media-io.ts#L251) holds presigned URLs; [SnowStagedMedia](../../../../plugins/qq-onebot/src/media-types.ts#L29) carries a private gateway path and its [driver](../../../../plugins/qq-onebot/src/driver.ts#L403) also requires the original in-memory staged object and peer. None of those URLs, QQ credentials, `file_info`, private upload handles or paths goes to server Config/State/events, model context, UI or ordinary bridge JSON.

- **Inbound:** local native adapters keep the official fixed-CDN/DNS/pinned-download policy and OneBot authenticated-peer media routing. Following server admission and current captured grant checks, the server requests only the known material slot from the exact source/peer/event. Stream bounded byte chunks with credit/backpressure, sequencing, cancel/actual settlement and byte-count/hash checks; validate kind/content and bind the resulting server `HostMaterialStore` object to its canonical audience/input. The existing [TaskMediaPeer usage](../../../../apps/companion-service/src/qq-media-transfer.ts#L197) and [media limits](../../../../packages/contracts/src/media.ts#L14) are good local building blocks, but the existing pipe implementation does not itself provide network framing/authentication. Keep the actual per-kind/aggregate/staging limits in [contracts](../../../../packages/contracts/src/companion-material.ts#L15); never pack a 32 MiB file into control JSON.
- **Voice:** transport encoded source bytes, not a local host path, to the server-authorized consumer; server [QQAudio](../../../../apps/companion-service/src/qq-audio.ts#L343) already owns codec→ASR and semantic material work. In the other direction server TTS→verified SILK follows accepted text before bounded encoded bytes return to the original local source. The existing [codec manifest](../../../../plugins/qq-media-codec/plugin.json#L9) and [pin](../../../../plugins/qq-media-codec/codec-image.lock.json#L75) are Linux-x64 Docker facts. Run that owned computation on its supported server or propose and prove a real Windows codec separately; do not load the Linux image/binary as a Windows host capability, require unselected local Docker, or rename PCM as SILK.
- **Outbound:** the server first owns/finalizes the immutable route, message IDs, parts, seq, budget and State claim ([delivery](../../../../apps/companion-service/src/qq-delivery.ts#L486), [SQL claims/recovery](../../../../plugins/state-sqlite/src/deliveries.ts#L461)). For a claimed media part stream the exact authorized canonical material and hash to the captured local source; local native code performs the existing upload/send under the same peer/route. If upload and send are separate attempts, keep the actual staged native object solely in a bounded local per-source/peer/part slot addressed by the server's already-known part/attempt identity, with exact route/connection checks; a serializable ID is correlation only, never a bearer right. Local restart, peer replacement, revoke or expiry invalidates the slot. For OneBot `upload-and-send`, preserve it as one platform publication. Send only the bounded public receipt/outcome and independent cleanup facts back; never return the native staged value in `uploaded`.
- **Previously observed group files:** current server [work preparation](../../../../apps/companion-service/src/qq-media-transfer.ts#L582) can later resolve a retained observation's file evidence. A bridge must preserve that feature without a local shadow conversation DB or exposing a private reference: either import eligible observation bytes to server-owned scoped material under a bounded, policy-authorized observation path, or retain an encrypted, bounded local source-owned reference index keyed by canonical observation/slot with expiry and exact account/source checks. These are implementation alternatives with different eager-transfer and persistence costs; the bridge must explicitly select/prove one rather than silently lose the feature after reconnect/restart. Missing/revoked local evidence is unavailable, never an invented file.

## Once-dispatch, confirmation and cleanup

A server claim is durable **before** local egress. A local authorized dispatcher must accept the claimed `{delivery, part, attempt, operation, source binding, native connection}` once, recheck the exact local source/lease and never resolve a replacement by account after an await. The existing [official](../../../../plugins/qq-official/src/driver.ts#L347) and [OneBot](../../../../plugins/qq-onebot/src/driver.ts#L228) drivers already require `expectedConnectionId`; reuse this invariant. Include server-issued attempt ID and exact peer identity in every request/report and match the server claim before updating it.

Report separately: not dispatched, dispatched with no authoritative receipt, actual accepted/rejected receipt, and real local cleanup outcome. A fully observed receipt remains a fact for its original target even if later authorization/transport cleanup fails; do not expose private upload values as a receipt. If the bridge dies after dispatch and before evidence arrives, the server records **unknown** and never automatically replays. A late locally observed receipt, if the same local process still has evidence, may be reconciled only against the original frozen attempt/source identity and without authorizing a new dispatch. If evidence was lost in a local crash, unknown is the truthful result: there is no exactly-once network guarantee or need to create a local shadow delivery DB. Server recovery already treats in-flight attempts as unknown ([State recovery](../../../../plugins/state-sqlite/src/deliveries.ts#L567)). Honor canonical native sequence/quota allocation across batches and mandatory-text-before-voice.

## Windows x64 build and operational implications

The two QQ protocol manifests already claim Windows x64; that declaration is not a native Windows end-to-end test. Current [desktop build](../../../../apps/desktop/build.mjs#L13) builds plugins/Main/preload/worker/renderer and emits admission evidence; [package scripts](../../../../apps/desktop/package.json#L16) and [start script](../../../../apps/desktop/start.mjs#L19) describe a workspace developer launch. Packaged resource lookup exists in [Main](../../../../apps/desktop/src/main/index.ts#L227), but the inspected files do not establish a complete distributable.

A first handoff **proposal** is a versioned, self-contained Windows-x64 portable application directory, with an explicit start/stop path and a real writable user-data location; no installer, auto-start, signature or public release is implied. Validate that its app is actually treated as packaged: current [unpackaged startup](../../../../apps/desktop/src/main/index.ts#L188) redirects user data to a workspace-relative `.cache`, which is not an acceptable assumption for a portable application moved to an arbitrary path. Include actual Electron/runtime, worker, packaged admitted QQ plugin artifacts and manifests, required `ws`/other runtime dependencies, assets, fixed bridge protocol version, upgrade/removal instructions and an isolated profile. Verify source digests in the packaged layout, not only the workspace. Include the selected independent host process and an explicit stop path; no user-process installer or automatic startup is implied. Do not conflate a portable handoff with a signed or publicly published release. Do not assume the service's Node 26, Linux codec image, shell paths or Docker are available on Windows; prove that packaged Electron's actual runtime supports the selected local native IO.

The current OneBot adapter is a bearer-authenticated **reverse Universal** listener ([implementation](../../../../apps/companion-service/src/qq-onebot-io.ts#L55)); local does not mean a SnowLuma container shares Windows loopback. The user supplies the actual reachable interface/address and gateway configuration later; avoid silently binding a public interface, changing the existing container or transferring its token to the server. Any non-loopback deployment requires an explicitly protected listener/transport and firewall design rather than treating plaintext WebSocket bearer as confidential. Official QQ continues to use local fixed official API/WSS and local outbound upload/download, not a server-side official adapter.

## Minimum technical proof before proposing completion

These are future controlled gates, not evidence that tests have run in this research turn:

1. Real DesktopHost/PluginManager activation on the **actual** OS with each QQ plugin's admitted digest, local Config CAS/credential owner, source task and a concrete private port. Prove both factories/physical lifetimes work under the selected Main/worker or separate-process architecture, default exports remain fail-closed when uncomposed, denied/stale trust makes zero socket/credential use, and disabling waits actual worker, socket, credential and media settlement. Check cold restart, changed digest, source/key/account changes and `pending_restart` on cleanup failure.
2. Fresh isolated server Agent and local desktop/host use a controlled authenticated bridge, never original profiles, real QQ/SnowLuma or paid models. Prove one server Agent/State identity and no local Core/State copy. Exercise official and OneBot, private and group, authentic locally controlled peers, direct and group observation/wake/proactive judgment, policy changes and member/admin scope. Verify a forged role, cross-account peer, stale source generation or substituted connection causes no admission/effect.
3. ## Decisions and handoff

**Confirmed facts:** server owns Agent/State/policy/cloud work; both QQ protocol natives and secrets must be local. Existing local kernel, trust, CAS, secret and bounded-media primitives are reusable, but default QQ worker activation and a remotely authorized bridge are not implemented. Existing voice codec pin is server/Linux-specific.

**Technical recommendation:** use an independently running local host built on the existing kernel and PluginManager, with source-only native ports and a server remote-source facade; keep M6 server admission/delivery/ASR/TTS and replace only the physical source boundary. A first personal-use proposal is existing owner bearer plus TLS and a fixed QQ bridge, with an explicit statement that the bearer retains full owner authority. Keep private native references local. Compare the actual small `CompanionPluginHost` composition with a headless `DesktopHost`/worker in Phase 0 rather than claiming either already implements the bridge.

**Selected:** QQ keeps running when the desktop process explicitly exits. Desktop local source controls and server-Web policy management are the current proposed UI ownership in [the PRD](../prd.md#L51); review concrete implementation without duplicating either owner. A versioned portable Windows handoff is the proposed first target; no automatic OS startup or public release is implied. No source, profile, container, account or live network state was changed in this investigation.
