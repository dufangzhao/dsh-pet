# G0 — local QQ kernel slice

This is evidence for the local kernel slice, not completion of G0 or product acceptance. It covers an isolated test composition and no live QQ, model, original data, SnowLuma or AstrBot connection. Tests were run on the current Linux x64 host; this is not Windows-native evidence.

## Implemented boundary

- `createLocalPluginKernel` creates an in-process `CompanionPluginHost` with exactly the official and OneBot QQ plugin registrations; no `CompanionRuntime`, Core or SQLite State instance is created. Its private ports are supplied by the trusted host composition, not JSON. Both registrations use their real `create*QqPlugin` factories and start disabled.
- The caller provides a preset; a new opt-in `sourceTrust: 'review'` mode leaves that policy intact but requires explicit confirmation of the exact boot-pinned package digest. The old service default remains preapproved. The selected source directory must resolve to the real `@pet/qq-official`/`@pet/qq-onebot` package from which the current process loaded its factory. Mismatched directory/manifest is refused. The factory package digest is pinned synchronously when the kernel module evaluates, before `createLocalPluginKernel` can be called. A change between import and creation is rejected as well as changes afterward. After a source digest changes, neither the old nor the new digest may be confirmed in this host; stop and restart/discover before reviewing the changed source. There is no hot-load fallback.
- Source Config provided at creation is an initial seed only; existing ConfigService records are not overwritten on restart. Subsequent changes use the existing Config CAS. Trust is process-local in this slice, so a new host requires new explicit review.
- Local `runFor` captures the actual active source generation, combines its source signal with caller cancellation, and acquires a declared source read lease inside the existing supervisor task. Trust/preset withdrawal aborts that lease and cancels the same task; the lease remains owned until physical work settles. The captured owner generation and permission epoch prevent deny→allow or trust withdrawal→reconfirmation from reviving the old context; disabling and draining it precede a new generation. Disable blocks same-source enable and new source work until the plugin's actual disposer and all tracked work of that exact generation settle. Review reports `pending` during that drain and `failed` for unconfirmed cleanup; failure prevents a replacement. Other sources remain independent. Host close is idempotently joined.

## Actual checks

- `packages/local-host`: `node node_modules/vitest/vitest.mjs run src/kernel.test.ts` — 3 tests passed. Real factory activation used controlled official WebSocket and OneBot reverse-WebSocket peers, synthetic credential/token and local-only endpoints. Test checks absent initial trust, failed/wrong review, distinct preset, no native fetch at activation, real credential/permission leases, source digest change before any subsequent send, exact-source revoke, independent peers, gated native disposer and gated source-task physical drain, replacement fencing, failed cleanup/pending_restart, and Config CAS persistence across a fresh host.
- `packages/companion-runtime`: `node node_modules/vitest/vitest.mjs run src/local-host-trust.test.ts src/source-authority.test.ts` — 12 tests passed, including existing service-default behavior, explicit trust, a retained deny preset and source fingerprint failure.
- Direct TypeScript checks of `packages/local-host` and `packages/companion-runtime` passed. Scoped ESLint passed for the two local kernel files plus the two companion-runtime files.
- The fixture uses temporary directory symlinks pointing at the actual installed QQ package roots. It replaces only the temporary official link with an unrelated local directory to simulate source change; it does not mutate the real QQ package. The isolated data root initially contains only the configuration directory; the manager lists only the two QQ sources.

## Limits and remaining proof

The host is a G0 in-process composition, not the independent daemon, bridge, user UI, shipping package, or a substitute for them. Native IO was supplied from the existing service helpers solely by the G0 test; shared portable extraction and the production source controller are future work. `TaskHandle.settled` proves the callback returned, not by itself that a swallowed native cleanup error became visible: source implementations must continue to surface failed physical cleanup through their real disposer/cleanup result. The failed-disposer regression proves that explicit failure is retained rather than permitting replacement.

`import.meta.resolve` plus package-root equality proves that the tested unbundled package resolution and boot-loaded factory come from the same installed package location; it does not prove a future bundled executable has the same property. The package gate must keep factories external and resolve the correct reviewed package with the same SDK/kernel instances, or generate and verify equivalent builtin-admission/source-pin evidence for the actual embedded factory. It must test the portable layout independently of this checkout and reject stale source after a rebuild. Real Windows packaging/runtime and standalone host lifecycle remain separate gates.
