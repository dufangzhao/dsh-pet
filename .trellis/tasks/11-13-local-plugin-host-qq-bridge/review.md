# Independent planning review — local host / QQ bridge

Reviewed 2026-11-14 against product HEAD `6897787`. This review read the current PRD, design, implementation plan, all four research notes and the relevant existing source. It includes the revised design rule requiring a **fresh bounded server check before each external QQ business request**, without an authorization cache or new lease/ticket table.

Only this document was written. No product/test/dependency change, build, process, model, account connection, SnowLuma inspection or acceptance run was performed.

## Conclusion

**No additional blocking design finding for starting G0 was identified.** The selected independent host and narrow remote-source facade are implementable extensions of the existing owners. The design no longer treats a service-hosted adapter, builtin admission, worker JSON or an owner bearer as an already working local-device bridge.

G0 remains a proof gate, not permission to waive a contradiction or a claim that the target package already works. Implementation is still contingent on the user's final approval of the complete proposal, including the Windows-first portable defaults. This review does not authorize task start.

## G0 acceptance details to retain

These are concrete implementation checks for the chosen architecture, not new product decisions or additional frameworks.

1. **Prove the complete core-less call chain.** [CompanionPluginHost.owner/run/call](../../../packages/companion-runtime/src/plugin-host.ts#L399) still assume a default host consumer in several helpers. G0 must either register the minimal inert host consumer or route source-owned work through the existing `runFor`; it must not instantiate CompanionRuntime/State to satisfy an accidental dependency. The existing [host definition](../../../packages/companion-runtime/src/core-plugin.ts#L97) is inert and its consumes are optional, so this is a tractable composition check. Keep the current server composition's behavior unchanged.
2. **Separate GUI and daemon singleton namespaces.** The GUI currently takes [Electron's single-instance lock](../../../apps/desktop/src/main/index.ts#L202). The headless mode must branch before GUI startup and use its own profile/lock identity, so the two processes can coexist while a second daemon for the same daemon profile is rejected. Reattach must prove the expected boot/protocol/package identity, not merely trust a discovery file's PID or label. Failed cleanup must not free the daemon/source slot early.
3. **Keep the fresh-check rule literal and finite.** [Design §6](design.md#L92) now requires a fresh check for the exact claimed attempt/route/part/hash/current bridge before a new external business request. Demonstrate delayed, lost and retired responses cannot start a new request, with the local five-second elapsed budget and server eligibility still enforced. Do not add a renewable authorization cache to avoid the check. Identify transport housekeeping separately from new publication/download/upload operations when wiring the existing native primitives. A request already dispatched may still complete after partition; report its receipt independently of cancellation/cleanup.
4. **Keep late facts fact-only.** Persist the execution binding atomically with its remote claim. Keep the absent-binding service-local fingerprints unchanged through format3→4 and older composed migrations. A new boot/session/account cannot redeem an old private upload continuation or execute the old claim. An authenticated reconnect may submit exact retained evidence for the original binding without receiving new execution authority. Participant revocation can block new effects but cannot rewrite an already accepted external fact. Contradictory receipt IDs remain conflicts.
5. **Keep the two Agent links independent.** Personal HTTP/SSE/ASR/Pet playback retain their current Main-owned connection and shutdown. The daemon's bridge has a separate connection ID, abort scope and private bearer copy for the same selected Agent. Old Main connection state must not dispatch through the daemon, and a GUI reconnect must not retarget a frozen QQ plan. Show the actual Agent target of the daemon if it differs from or is not yet attached to the personal client; require an explicit reconnect action rather than silently copying a new target into old effects.
6. **Treat the package proof as a target-runtime proof.** Resolve the headless entry, factory registrations, shared native package, assets and runtime from the extracted layout outside the checkout. Windows-first portable delivery needs a matching runtime/architecture and a later actual Windows smoke result. A Linux two-process proof may close the portable layout/contract gate but cannot be reported as a tested Windows client. This is an evidence dependency, not a reason to broaden into installers, signing or OS-start registration.

## Authority and data conclusions

- Existing-owner bearer reuse is consistent with the stated trusted single-owner daemon model. It retains full owner authority; host/source IDs, digests, boot IDs and registration messages are captured routing/evidence **assertions by that trusted client**, not independently attested device identity or a security boundary against another holder of the same owner bearer. The design states this honestly; no PKI or multi-device zero-trust layer is required.
- Local source trust/permissions and server participant/policy checks are independent. The existing [QQ authority wrapper](../../../apps/companion-service/src/qq-native-types.ts#L39) and [withSourceAuthority](../../../packages/companion-runtime/src/source-authority.ts#L6) already provide the relevant source-owned task/credential/actual-settlement seams. A narrow shared extraction can preserve them; serializing the callbacks or treating a received OwnerRef as a task signal cannot.
- Server policy, grants, canonical material bytes, model purposes, codec and cloud work remain server-owned. Platform secrets, signed/raw native download/upload references and OneBot paths stay with the daemon. The bridge carries bounded bytes and opaque purpose-owned references, not those native objects. Losing the local endpoint does not revoke the recorded authority of already accepted cloud work.
- Format4 is justified by the private immutable execution binding and late-fact semantics. It is not justification for another canonical send table, replay queue or generic remote-job ledger. Offline unattempted output stays blocked, while accepted/unknown effects are never automatically reissued.

## Nonblocking simplifications and UX

- Keep the local composition change narrow: a reviewed trust/approval hook or shared composition helper is sufficient. Do not clone DesktopHost and CompanionPluginHost wholesale or create a second permissions registry.
- Start with one closed QQ bridge and one local management facade. Existing control/media/sensitive primitives can share a physical authenticated transport while preserving their distinct schemas and budgets; separate managers or a universal RPC layer are unnecessary.
- Local source settings/key/trust/lifecycle belong to the daemon, and policy/judge/canonical delivery management belong to the server. This requires explicit labels, captured owner/CAS baselines and disabling the wrong writer, **not four separate screens**. A single desktop page may show both domains with the existing open-Web action for server management.
- The old open-Web exposure allegation is not a finding: the generated facade enumerates methods, and the M6 production-Electron evidence already exercised it. Preserve that regression rather than invent another opener.
- Preserve process-only key behavior. GUI exit must not clear a running daemon's key slots; daemon exit/restart does not imply encrypted persistence exists. Avoid passing bearer/QQ keys via argv, environment, ordinary control JSON, URLs or discovery records. Do not create a separate secret store to improve convenience.

## Follow-up — remote uncertainty must not poison the global sender

The additional source finding is substantive: changing only the sender's exception-path `cleanup: 'settled'` is insufficient. The existing sender [latches every non-settled cleanup globally](../../../apps/companion-service/src/qq-delivery.ts#L626), [rejects all later delivery](../../../apps/companion-service/src/qq-delivery.ts#L211), and [fails close from that latch](../../../apps/companion-service/src/qq-delivery.ts#L835). Directly reusing this behavior for a lost remote acknowledgment would permanently poison otherwise usable sources even after read-only outcome reconciliation.

**The scope of this P1 is now closed in the design, not fixed in product code.** Revised [design §6](design.md#L96) and [G0/G5](implement.md#L12) distinguish service-owned physical drain failure from a remote-unconfirmed hold on the original captured source/native-task/claim. Only matching actual settled-cleanup evidence or explicit same-host owned-resource recovery releases that hold; another boot/config/socket announcement alone cannot. The old effect/outcome may remain unknown, but neither the old attempt nor its TTS/controller gate is reopened. Unrelated sources remain usable. Server shutdown joins its own resources and durably preserves remote uncertainty; it does not claim to have stopped the daemon.

The new G0 proof is the correct regression: lose the acknowledgment, reconcile the same-boot facts without effects, then successfully publish a new input while the original native effect count stays exactly one; separately prove a bare new-boot announcement does not clear an unresolved hold. Actual local-host cleanup failure still retains its physical slot, and a real service-owned drain failure retains its existing fatal behavior. No extra ledger, replay mechanism or generalized recovery framework is required. This follow-up only reread the stated source/design sections and appended this document; no implementation or test ran.

## Final convergence — custody, reporting and management attach

The final clauses satisfy the existing G0 obligations; no further planning blocker was identified:

- [Raw custody](design.md#L80) requires every required local reader to terminate/join, verified stream EOF/size/hash and committed owned server staging under the still-valid original actor **before** codec/ASR. Only then does server actor/task lifetime replace local source lifetime. A source-only postflight failure cannot erase that committed fact; actor withdrawal still aborts processing. Raw staging is not a ready MaterialRef. The paired disconnect/revoke checks are explicit in [G0/G4](implement.md#L13).
- [Native outcomes and reporting](design.md#L94) bind the actual local kernel task once at the first positive pre-IO check. A known result is retained by its bounded local operation before RPC reply. [Fact reconciliation](design.md#L108) uses a current authenticated reporting envelope carrying the original immutable execution binding/task/attempt, so closing an old ControlEndpoint does not lose the only true outcome. Reporting cannot execute the old request, redeem its continuation or reopen TTS.
- [Management attach](design.md#L36) now has a concrete protected same-user per-boot capability/rendezvous, a fixed native-read endpoint and boot/protocol/package checks. It carries no Agent/QQ keys and is not exposed to renderer URLs. SensitivePeer remains the entered-secret plane, not authentication. Restart still requires process-only credentials to be entered again.

These are design-level closures only. They neither prove the gates passed nor expand the trusted-owner bearer model into device attestation, PKI, a new ledger or another source of execution authority. The original final-approval and target-runtime acceptance limits above remain unchanged.
