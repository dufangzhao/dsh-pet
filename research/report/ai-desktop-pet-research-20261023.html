LANDSCAPE

成熟桌宠、AI 框架与素材平台，要分组看

纳入已有公开发布或持续维护线索的代表项目。“成熟”分成桌面产品成熟度与 AI 链路成熟度；有 Steam 发行，不等于 AI 能力已完善。

你的目标：能力模块优先，外观模块可替换

默认展示全部项目。实用功能重点看N.E.K.O与AIRI，语音接口参考Open-LLM-VTuber；桌面入口参考两个指定仓库，宿主生态参考VPet。

AIRI：TS团队优先参考，仍需冻结版本

源码 Electron/Vue/TS；Live2D依赖Pixi，3D依赖Three.js/three-vrm。语音管线有分段TTS、队列、打断；有视觉编排和MCP工具桥。

优：多渲染器与provider模块适合重组。劣：monorepo与原生集成复杂，beta和main可能不同步。

记忆纠偏：README仍写WIP，但store已有localStorage事实记忆；既不是完全没有，也不能夸成成熟RAG。

发行：本次查到v0.12.0-beta.6多平台包，非稳定性保证。代码MIT，角色与SDK另审。

Open-LLM-VTuber：语音接口清晰，重写期需留意

源码 Python/FastAPI会话层接ASR、Agent、TTS，Electron/React前端播放音频与Live2D。支持本地/云提供方组合，MCP客户端可启动外部进程。

优：音频处理与Agent分层明确，可逐项替换。劣：前端、Python与模型需组合部署。

记忆纠偏：官方明确长期记忆暂移除；聊天日志仍保存。v1.2.1的exe/dmg只是前端，不是全模型整合包。

维护：v2重写在规划，v1继续修bug。MIT不覆盖所列Live2D样本资产。

N.E.K.O：实用能力覆盖广，权限面也更宽

优：语音、视觉、记忆、工具和多角色形态整合广，适合作功能参照。劣：进程、供应商、插件和权限面更复杂。

建议的首版组合

Electron/TS宿主 + 按键录音 + sherpa-onnx语音提供方 + 可替换TTS + 独立听写注入插件；角色先用可合法分发的轻量资源包。第二步加入DSH/独立Agent适配器、只读窗口理解；最后开放UIA/浏览器操作。音色制作工具与本地GPU服务按需安装，不捆绑全部环境。

PLUGIN FIRST

一个小内核，三类扩展，不让插件互相绑死

推荐 Electron + TypeScript 做桌面宿主与 SDK。计算密集型语音用 Python/原生 sidecar；电脑操作通过受控适配器。DSH Bridge 是可选的一种 Agent 后端，不是全系统唯一依赖。

能力插件

代码或独立服务，提供识别、合成、视觉、操作等能力。第三方原生代码须明确标为高信任，不默认加载。

角色 / 声音资源包

声明式资产：模型、动画映射、性格、音色引用与许可清单。默认不允许携带任意脚本。

用户配置 / 工作流

选择能力、模型、声音、角色和快捷键。同一套底层规范下保存“离线听写”“屏幕助手”等配置。

先冻结这些底层契约，再写插件

契约最小规则为什么不能省
清单与版本id、version、apiVersion、capabilities、permissions、configSchema、依赖与资产许可证拒绝不兼容版本；安装不等于启用或授权
生命周期install → configure → activate → health → deactivate / dispose；异常可隔离重启停用插件必须释放麦克风、GPU会话与任务
请求与事件requestId / sessionId / traceId、类型化输入输出、错误码、deadline、cancel不串会话；能取消、定位失败与重试
媒体时序编码、采样率、声道、时间戳、seq、end；有界队列、背压、优先级打断后不能继续播放旧音频；视频不能挤爆事件总线
能力发现声明 streaming / interruption / offline / languages / voice-design 等实际能力不要假定每个TTS都会克隆声音，每个模型都会看图
权限与数据按窗口/应用/目录/域名授权；数据标签、密钥句柄、存储配额、审计插件不能直接读取其他插件密钥或全部屏幕内容
兼容验收契约测试、假供应商测试、版本锁定、迁移回滚、故障与越权测试“符合规范”必须可运行验证，而不是口头约定
接口怎么拆，才不会越拆越乱？

AudioSource → STTProvider → Transcript；听写分支交给 TextInputSink，聊天分支交给 AgentBackend。

VoiceDesigner → VoiceProfile 与 TTSProvider(text, voiceProfile) → AudioStream 分开。角色只订阅音量、口型或情绪事件。

ScreenSource → FrameRef → VisionProvider → Observation；ComputerActionProvider 另接经过许可的结构化动作，并返回执行回执。

原生语音模型实现独立 RealtimeSession 能力；不要强行拆成三次云调用。所有接口还需能力协商、取消与错误语义。

统一协议，不代表所有数据都走 MCP

建议控制面用 JSON-RPC + JSON Schema，经 stdio / 本地IPC或带身份校验的本地服务通信。音频与帧引用走专用有界流，避免不断把大块base64塞进全局事件总线。

MCP适合工具与资源生态接入；插件安装、GPU生命周期、音频背压、实时打断和界面扩展仍由宿主协议定义。

不让插件A直接import插件B。由宿主按能力选择实现，失效时降级或停用；同一用户配置可替换不同供应商。

进程隔离不是自动安全沙箱

sidecar能隔离崩溃，却可能仍以当前用户权限访问文件与网络。优先使用受信任插件、最小OS权限与明确授权；第三方本地代码不能只凭一份manifest就宣称安全。签名证明来源，不证明无恶意。

建议的开发策略

小内核自行控制；借鉴 dsh-pet 的宿主桥接与独立入口、Open-LLM-VTuber 的语音接口、AIRI 的渲染/管线、N.E.K.O 的多能力整合。先做 DSH Bridge 或直接模型适配器中的一种，再用第二种验证解耦。不要一次性 Fork 多套桌宠后硬拼。
