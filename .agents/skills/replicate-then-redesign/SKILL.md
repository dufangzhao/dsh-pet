# Replicate, verify, then redesign

Keep the working capability while changing how people discover and use it. A screenshot proves appearance; it does not prove an action is connected. A new layout is not a new runtime.

## Start at the actual phase

Identify the target surface, reference version/source, existing implementation, requested number of options and requested model/expert roles. Inspect supplied artifacts before asking for missing facts. Reuse an accepted replica and its current evidence; do not repeat the replica phase just because this skill was invoked.

Respect the requested output stage. A read-only audit or plan ends with scoped gaps and implementable briefs; it does not imply product writes or native operations. Trace only the boundaries needed for the surface and decision, rather than reading the whole project.

For reusable output formats, read [the evidence template](references/evidence-template.md). Use the repository's existing task/spec tools when present; this skill does not require a particular project manager, framework or model provider.

## Establish the capability contract

For each visible action, trace control → existing handler → API/runtime → actual effect → returned UI state. Include meaningful failure, cancellation, unavailable and pending states. Record the owner of configuration, history, capture, credentials and active tasks.

Classify the evidence accurately: observed in reference, inferred from source, implemented locally, verified with a controlled service, verified against a live service, or still missing. Record the exact reference version; a README image may show an older UI than the checked-out source.

Answer implementation-ownership questions directly: which layers reuse a framework, which are independent adapters, which behavior was matched to the reference, and what remains unverified. Do not say the whole backend is copied or complete merely because the screen matches.

If functional gaps remain, implement the necessary adapters on the existing architecture before calling the replica complete. Preserve its permissions, save/apply receipts and cancellation rules. If reference fidelity conflicts with current authority, capacity or cancellation scope, record the exact difference and propose an adapter decision; do not silently weaken authority or reduce an existing capability. Do not create a second agent loop, recorder, history, credential store or shadow configuration to make a prototype seem connected.

## Reproduce only what is needed

Use reference source/runtime evidence to reproduce the agreed scope. Match behavior as well as labels and placement. Do not transplant product code or artwork without the required authorization/license. Standard protocol facts and independently written adapters are different from copying a product implementation.

Use existing tests and a real application window where available. Explicitly labelled state studies may illustrate a failure or loading state, but they are not evidence that the real operation succeeded. Resolve actual parity defects; list broader unresolved scope precisely instead of inventing inert controls.

## Freeze behavior, explore the interface

Treat the verified capability contract as the baseline for redesign. Capture the relevant action/state regressions so structural changes cannot silently remove functionality or turn stored data into a false success message.

Honor the user's model choice. Discover an allowed route and actual effort level before delegating; report an unavailable route without pretending it ran. Use suitable enabled specialists for visual direction, UX architecture and implementation/review when their work adds value. Their reports inform the design; coverage counts alone do not validate it. Check the actual shared worker budget before parallel dispatch. If consultation fails or only some reports return, record that partial coverage and continue from available evidence; a dispatch acknowledgement is not a completed review.

Generate the number of options requested. Make each option differ in information hierarchy, task order, spatial organization or interaction—not only color and border radius. Explain its primary user situation and tradeoff. Keep common identity, semantic state and icon/component rules coherent across options.

Use available design guidance selectively. The user's product and reference constrain the exploration; a generic design-system search must not replace them.

## Establish an independent component language

When the user wants a product of their own, redesign includes the controls and interaction vocabulary, not only page grids. Inventory the reference's identifying primitives: buttons, fields, provider/item pickers, segmented tracks, badges, notices, menus, preview tools and theme chrome. State which must be replaced.

Define one coherent original kit with typography/spacing/surface/radius/color/motion rules and real normal, focus, disabled, pending, error and selected states. Build a small component/state board so that the vocabulary can be inspected before it is spread across options. Use a fitting licensed set or design the set; a collection of unrelated gallery snippets is not a design system.

Separate functional reuse from presentation reuse. Reuse controllers as state and action callbacks. Do not feed old fully rendered JSX controls into different layout slots and call the result original. A shared rendered slot is suitable only after its actual controls have been redesigned. Renaming CSS classes or applying a new palette to the old widget is not evidence of replacement.

Apply the new kit consistently to all relevant options and their shared shell. Keep the original character or assets when they belong to this product; do not preserve a reference's builtin theme names, copied palette identity or characteristic control forms merely because they were present in the replica. Migrate saved builtin selections when needed without losing user-created schemes or other data.

Review close views of controls as well as whole windows against the rejected reference. If fields, pickers, feedback and preview tools still read as the reference after the layout is removed, the originality work is unfinished. Structural difference and functional parity remain separate requirements.

## Research components and icons

Visit the user's specified sources. For each material actually adopted, record its exact permalink or repository/version, author, license evidence and adaptation. A gallery calling itself open source is not sufficient evidence for every asset. If a license is unclear, keep that item as inspiration or choose a verified alternative.

Choose one compatible glyph family, stroke/size rule and motion language. A morphing engine is not an icon pack: verify both the engine and the glyph source. Use morphs to express a real state change, and provide a reduced-motion/static equivalent. Select a small number of fitting microcomponents rather than combine unrelated showcase effects.

Adapt styles to scoped classes and existing tokens. Keep external examples, analytics, remote fonts and arbitrary scripts out of the shipped view unless the task actually requires and authorizes them. Preserve required attribution. Prefer the smallest suitable dependency surface; do not write a replacement animation library just to avoid a verified small package.

## Implement reviewable options

Reuse the current action/controller layer and extract only the presentation seams needed by the options. For original-control work, that seam must expose behavior independently of the reference widget markup; new controls render that behavior through the new kit. Keep long-lived capture, subscriptions, drafts and credentials in their authoritative owners. Changing an option must not start another microphone or duplicate service requests. Trace what actually remounts when a layout, dialog or permission prompt appears; define which drafts survive those seams instead of assuming a shared runtime preserves component-local input.

When the user is choosing among options, provide an isolated review entry or equivalent concrete prototypes. Keep the normal application/profile available. Do not silently pick a production winner; if the user already authorized a chosen design, implement that choice directly without adding another approval gate.

Use real controls and actual receipts. Draft vs saved vs tested vs applied are separate states when the underlying system distinguishes them. Put status and errors where people act, and preserve useful drafts after rejection/conflict.

Maintain a clear scope for local presentation state such as an open drawer or preview lighting. Do not present a local animation or echo as an agent reply or persisted preference.

## Verify behavior and visual quality

Test shared business logic once at its real boundary, then exercise each layout's reachable actions, state presentation and responsive/focus behavior. Add a regression when a real interaction breaks; avoid duplicating the same backend test for every skin or testing only generated wording.

Use actual target windows at comparable viewport/zoom/DPR. For desktop views, check the supported minimum size and keyboard zoom. Verify keyboard/pointer activation, menu/focus transitions, error/readiness states and reduced motion. Check visible effects against their real receipt, not only component markup.

For capture/chat surfaces, verify the same owner and record survive navigation. A visible button is not another recorder; assert actual ownership and device/request behavior. Do not bypass consent to make a recording test pass.

Keep private inputs out of logs, traces and comparison screenshots. Use isolated test data and bounded cleanup. Do not use real paid/account operations merely to validate a layout when a controlled-service test can establish the relevant contract; keep the distinction in the result.

Inspect the screenshots and implementation together. If all options are interchangeable generic cards, return to the design decision that caused it rather than add decoration.

## Deliver

Match deliverables to the phase: a plan supplies its evidence, gaps and design briefs without a runtime-pass claim; an implemented redesign supplies the working review entry, versioned screenshots/comparison, capability parity result and adopted-asset ledger. State real limitations once. Separate the user's design choice from subsequent production refactoring when that is the agreed workflow.

Capture reusable lessons in the owning spec/skill only when they change future decisions. Link the actual case artifacts instead of duplicating a second guide. Finish the repository's existing checks/commit process within the user's authorization; this skill grants no publishing, messaging, deletion or deployment authority.
